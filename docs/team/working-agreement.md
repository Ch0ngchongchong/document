## 연락과 응답
- 연락 수단: 급한 일과 일정은 팀 단톡방, 작업 내용 논의는 해당 이슈·PR 댓글. 단톡방에서 정한 결정은 이슈나 결정 기록에 옮겨 적는다
- 응답 기대 시간: 수업일에는 4시간 안, 수업이 없는 날에는 24시간 안. 늦어질 것 같으면 "확인함, 언제까지 답함"을 먼저 남긴다

## 작업 방식
- 브랜치 이름 규칙: `종류/이슈번호-짧은-설명` (종류: feat, fix, test, docs, logs). 예: `feat/12-unit-conversion`, `logs/daily-2026-10-27-yosi08`. 한 번 쓴 브랜치 이름은 다시 쓰지 않는다
- 한 PR의 크기 기준: 이슈 1개당 PR 1개, 변경 400줄 이하. 넘으면 나눌 수 있는지 먼저 본다 (일일 기록·개인 회고는 예외). 커밋 메시지는 `종류: 무엇을 했는지 한 줄`로 쓰고, "fix"나 "feat: file"처럼 내용 없는 메시지는 쓰지 않는다
- 리뷰 요청 후 기다리는 시간: 24시간. 그 안에 리뷰가 없으면 단톡방에서 리뷰어를 다시 부르고, 그래도 없으면 다른 팀원에게 요청한다. 데모에 필요한 PR은 당일 안에 리뷰한다

## 의견이 갈릴 때
- 결정 방법: 해당 이슈·PR에 각자 근거를 적고 30분 안에 논의한다. 합의가 안 되면 그 분야 역할 담당이 정한다 (기술 구조는 테크 리드, 기능 범위·우선순위는 팀 리더, 테스트 기준은 테스트 담당). 클라이언트 요구가 걸린 문제는 리더가 클라이언트에게 묻는다
- 결정 기록 위치: `docs/decisions/`에 `YYYY-MM-DD-주제.md`로 남긴다. 정한 것, 버린 안과 이유, 정한 사람을 적는다

## 결석·지각
- 인수인계 방법: 결석은 전날까지, 지각은 수업 시작 전까지 단톡방에 알린다. 진행 중인 브랜치를 push하고, 해당 이슈에 "한 것 / 남은 것 / 막힌 것"을 댓글로 남긴다. 그날 대신 맡을 사람은 팀 리더가 정한다. 스프린트마다 역할이 바뀔 때도 이전 담당이 같은 방식으로 남긴다
