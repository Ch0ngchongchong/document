# 5. MVP 가설, 기능 목록, 가정·위험, 클라이언트 질문지, 미팅 준비

> 목표: 우리가 만들 것과 모르는 것을 목록으로 만들고, 모르는 것을 클라이언트가 답할 수 있는 질문으로 바꾼다.

## 5-1. MVP 가설

> 클라이언트 미팅 전 우리의 추측입니다. 미팅 뒤 바뀔 수 있습니다. 제안서 Ⅰ-3 제안 범위, Ⅳ-10 목표 흐름의 바탕이 됩니다.

| 구분 | 내용 |
| --- | --- |
| 핵심 사용자 흐름 1개 (첫 데모에서 보여 줄 것) | 입고 검수 건 하나가 처음부터 끝까지 가는 흐름 (3-2). ① **명세서 업로드**: 물건이 오면 직원이 거래명세서 사진·PDF를 올린다 (업로드 대기 → 판독 중) ② **판독**: OCR이 글자를 읽고 LLM이 공통 JSON 필드로 정리한 뒤 품목 후보를 붙인다. 시스템이 발주와 다른 줄과 불확실한 값을 표시한다 (→ 직원 확인 대기) ③ **직원 검수**: 직원이 실물과 대조해 고친 뒤 확정한다. 발주와 모두 같으면 일반 건, 하나라도 다르면 예외 건이 된다 ④ **예외 사장 승인**: 예외 건은 사장님이 사유를 보고 승인하거나 반려한다 (→ 사장 승인 대기 → 승인 / 반려) ⑤ **재고 반영**: 일반 건은 직원 확정 뒤, 예외 건은 사장님 승인 뒤 시스템이 재고에 더한다 (→ 재고 반영 완료). 되돌림 경로: 판독 실패 → 다시 업로드, 반려 → 직원 재검수. 비교 기준이 되는 발주 건은 사장님이 미리 입력해 둔다. 근거: 3-2 상태 전이, 4-1 후보 A |
| 이 흐름에서 LLM이 쓰이는 곳 | ② 판독 단계만. 글자 읽기는 OCR이 하고, LLM은 공급처마다 다른 서식을 공통 JSON 필드로 정리하고 품목 후보를 매칭하는 일만 한다 (3-4 L1). LLM은 재고를 바꾸지 않는다. 확신이 없는 값과 규칙 검증에 실패한 값은 직원이 직접 확인해야 확정할 수 있다. 거래처 담당자 이름·연락처는 LLM에 보내기 전에 가린다 |
| MVP 테스트 범위 (이번에 확인할 것) | **카페 1곳, 약 150개 품목, 거래처 5곳**으로 제한한다. 이 범위에서 실제 명세서로 ①~⑤ 흐름이 도는지, 직원이 고쳐야 하는 칸이 얼마나 되는지, 예외 건이 얼마나 나오는지 확인한다. 거래처 5곳의 명세서 서식이 몇 가지인지도 함께 확인한다 (3-4 OCR+규칙 비교의 확인 필요 항목). 품목 수와 거래처 수는 미팅에서 실제 숫자로 고친다 [가정] |
| 확장 목표 (이번 MVP에서 확인하지 않음) | 매장 여러 곳, 업종이 다른 가게(식당·편의점 등), 품목 수백~수천 개, 처음 보는 거래처 서식. MVP 결과가 좋아도 이 범위에서 똑같이 된다고 말하지 않는다. 특히 품목 수가 늘면 비슷한 상품명이 많아져 품목 매칭이 어려워질 수 있다 [추정] |
| 당장 제외할 것과 이유 | ① 판매량 예측·발주 수량 추천 (3-4 L2, 후보 C): 판매 기록이 쌓여야 하고 예측이 맞는지 첫 데모 안에 확인하기 어렵다. 발주 수량은 사장님이 직접 넣는다 ② POS 연동으로 판매 시 재고 자동 차감 (후보 B): 외부 POS마다 연동 방식이 달라 시간이 오래 걸린다 ③ 공급처에 문자·앱으로 자동 발주 전송과 발주 취소 흐름: 공급처마다 주문 방식이 다르다 (2-2 순서 5). 발주는 비교 기준으로만 입력한다 ④ 반려 뒤 공급처 반품·재납품 처리 (3-1 R4): 공급처 화면까지 필요하다. MVP에서는 반려 사유를 남기고 검수 건을 닫는 데까지만 한다. 부분 입고는 예외 건으로 사장님이 승인하는 방식으로 처리한다 |

## 5-2. 주요 기능 목록

> 5~8개. '필수'는 첫 데모에 꼭 있어야 하는 기능, '선택'은 시간이 되면 만드는 기능입니다. 제안서 Ⅳ-11의 바탕이 됩니다.

| ID | 기능명 | 설명 | 사용자 | 우선순위 (필수/선택) | 관련 상태 전이 / LLM |
| --- | --- | --- | --- | --- | --- |
| F-01 | 상품 등록 | 상품명·바코드·매입 단가를 등록하고 고친다 (2-3). 거래명세서 판독 결과를 이 목록의 상품과 맞춘다 | 매장 직원 | 필수 | 상태 전이 없음. 재고 수량의 기준 데이터 |
| F-02 | 발주 작성·승인·취소 | 상품과 수량을 골라 발주를 만들고 승인한다. 공급처에 보낸 뒤 '전달 완료' 버튼으로 표시한다. 보내기 전이면 취소할 수 있다 | 매장 사장님 | 필수 | 발주 초안 → 발주 확인 완료 → 공급처 전달 완료 → 입고 대기 / 발주 초안 → 발주 취소 |
| F-03 | 거래명세서 판독 | 거래명세서 사진·PDF를 올리면 상품명·수량·단가 표로 정리한다. 거래처 담당자 이름·연락처는 LLM에 보내기 전에 가린다 | 매장 직원 | 필수 | 입고 대기 → 명세서 판독 / LLM (3-4 L1) |
| F-04 | 입고 대조·확정 | 판독 결과를 발주 내용과 나란히 보여 주고 다른 줄을 표시한다. 직원이 실물과 대조해 고친 뒤 확정하면 그 수량만큼 재고가 늘어난다. 확정 전에는 재고가 바뀌지 않는다 | 매장 직원 | 필수 | 명세서 판독 → 입고 확인중 → 입고 완료 |
| F-05 | 부분 입고·누락 문의 | 발주보다 적게 오거나 파손된 줄은 받은 수량만 재고에 더하고 부분 입고로 남긴 뒤, 공급처에 누락을 문의한다 (3-1 R3) | 매장 직원 | 선택 | 입고 확인중 → 부분 입고 → 공급처 누락 문의 |
| F-06 | 반품 처리 | 검수 중 불량을 발견하면 반품으로 돌리고, 반품 완료 시 반품 수량만큼 재고에서 뺀다 | 매장 직원 | 선택 | 입고 확인중 → 반품 → 반품 완료 (3-1 R4) |

## 5-4. 위험 요소

> 2~3개. 예: LLM이 틀린 답을 낸다, 개인정보가 LLM에 들어간다, 기능이 늘어나 8주 안에 못 끝낸다. 제안서 Ⅶ-17의 바탕이 됩니다.

| 위험                                                                                                                  | 일어나면 생기는 일                                                                                               | 대응 |
|-----------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------| --- |
| LLM이 거래명세서를 잘못 읽는다: 수량·단가를 틀리게 읽거나, 상품명을 F-01의 다른 상품과 맞춘다                         | 그대로 확정되면 재고 수량과 매입 단가가 틀어진다. 다른 상품으로 맞춰지면 품절이 아닌 상품을 또 발주한다          | 직원이 F-04에서 확정하기 전에는 재고를 바꾸지 않는다. 발주 수량과 다른 줄, F-01에 등록한 단가와 크게 다른 줄은 강조해서 보여 준다. 상품 매칭이 확실하지 않으면 자동으로 맞추지 않고 직원이 F-01 목록에서 고르게 한다. 판독에 실패하면 직접 입력으로 넘어간다 |
| 거래명세서의 개인정보가 LLM에 들어간다: 담당자 이름·연락처, 사업자 정보를 가리지 못한다                               | 거래처 담당자의 개인정보가 외부 LLM 서비스로 전송된다                                                            | 올린 사진을 LLM에 보내기 전에 가린 결과를 직원에게 미리 보여 주고, 직원이 확인해야 전송한다. 가릴 곳을 찾지 못하면 전송하지 않고 직접 입력으로 넘어간다. 판독 결과와 원본 사진은 우리 서버에만 저장한다 |
| 기능이 늘어나 8주 안에 끝내지 못한다: 공급처마다 거래명세서 양식이 달라 F-03 판독 품질을 맞추는 데 시간이 오래 걸린다 | 3주차까지 핵심 흐름(발주 → 명세서 판독 → 입고 확정)을 한 번도 돌리지 못하고, 필수 기능 F-01~F-04가 데모에 빠진다 | 필수 기능 F-01~F-04로 핵심 흐름을 먼저 완성한다. 판독은 클라이언트에게 받은 양식 1~2개로 범위를 정한다. 선택 기능 F-05·F-06은 핵심 흐름이 돌아간 뒤에 만들고, 시간이 부족하면 상태만 남기고 화면은 뺀다 |

## 5-5. 클라이언트 질문지

> 카테고리마다 1개 이상, 총 8~10개. 미팅 질문 시간은 팀당 약 12분이므로 우선순위 1~5번은 반드시 묻는 질문입니다. **1~3번은 제안서 Ⅶ-18에 넣어 미리 보냅니다.** 질문을 고칠 때 팀원끼리 서로 읽어 보고 예/아니오로 끝나거나 답을 유도하는 질문을 고칩니다.
>
> 좋은 질문의 조건: ① 예/아니오로 끝나지 않는다 ② 구체적인 사례를 들어 묻는다 ③ 우리 해결책을 정답으로 유도하지 않는다 ④ 답을 들으면 무엇을 결정할지 알고 있다.

| 우선순위 | 구분 | 질문 | 관련 가정 | 답변에 따른 결정 |
|---|---|---|---|---|
| 1 | 목적·성과 기준 | 현재 거래명세서를 재고에 등록하는 과정에서 가장 불편한 점은 무엇인가요? | 거래명세서 수기 입력이 주요 문제이다. | 핵심 해결 문제 확정 |
| 2 | 목적·성과 기준 | 거래명세서 한 건을 확인하고 입력하는 데 평균적으로 얼마나 걸리나요? | 입력 시간 단축이 의미 있는 효과를 낸다. | 목표 처리 시간 설정 |
| 3 | 규칙 | 거래명세서의 품목과 수량을 발주 내용과 대조하는 과정에서 오류가 자주 발생하나요? | 발주 내용과 입고 내역의 대조가 필요하다. | 대조 기능의 필요성 확정 |
| 4 | 사용자·권한 | 물건 입고 확인과 재고 등록은 주로 누가 담당하나요? | 사장님이나 직원이 입고를 확인한다. | 사용자 권한 및 역할 설정 |
| 5 | 규칙 | 거래명세서의 품목명이 실제 재고에 등록된 상품명과 다른 경우가 있나요? | 품목명 불일치가 발생할 수 있다. | 상품명 매칭 기능 범위 결정 |
| 6 | 예외 처리 | 주문한 수량보다 적거나 많은 물건이 도착하면 현재 어떻게 처리하나요? | 입고 수량과 주문 수량이 다를 수 있다. | 예외 처리 기능 우선순위 결정 |
| 7 | LLM 활용 | 거래명세서를 AI가 판독한 뒤 직원이 결과를 확인하고 입고를 확정하는 방식이 적절한가요? | AI 판독 결과에 대한 사람의 확인이 필요하다. | 입고 확정 절차 결정 |
| 8 | 데이터·연동 | 거래명세서는 주로 종이 사진, PDF, 엑셀 중 어떤 형태로 받나요? | 이미지나 PDF에서 정보를 추출할 수 있다. | 지원 파일 형식 결정 |
| 9 | 데이터·보안 | 거래명세서에 개인정보나 외부 AI에 전달하면 안 되는 정보가 포함되나요? | 개인정보를 마스킹해야 할 수 있다. | 데이터 마스킹 및 처리 정책 결정 |
| 10 | 범위·우선순위 | 첫 버전에서 반드시 필요한 기능과 나중에 추가해도 되는 기능은 무엇인가요? | 거래명세서 판독과 입고 확인만으로도 핵심 가치를 제공할 수 있다. | MVP 범위 최종 확정 | 

> 질문지를 Claude에게 보여 주고 '빠진 관점'을 물어본 결과는 [ai-check-log.md](../domain/ai-check-log.md#질문지-검토-5단계)에 적습니다.

## 5-6. 미팅 역할 분담

> 실제 클라이언트 미팅에서 다섯 명이 하나씩 맡습니다. [팀 역할](../team/roles.md)과 따로 정해도 됩니다.

| 역할 | 하는 일 | 담당 |
| --- | --- | --- |
| 진행자 | 질문 순서·시간 관리, 꼬리 질문 | 신은총 |
| 기록자 | 답변을 말 그대로 기록 | 김가은 |
| 꼬리 질문자 | "예를 들면요?", "그 경우 누가요?"로 파고들기 | 진수화 |
| 시간·가정 체커 | 남은 시간을 알리고, 미팅에서 확인된 가정을 표시 | 권기범 |
| 요약·확인자 | 끝나기 1분 전, 들은 답을 3문장으로 되읽어 클라이언트에게 맞는지 확인 | 김지운 |
## 5-7. 미팅 전에 다시 볼 것

> 제안서를 보낸 뒤 미팅까지 팀이 함께 확인합니다.

| 확인할 것 | 메모 |
| --- | --- |
