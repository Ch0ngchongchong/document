## 최종 선택

- 선택한 안: B안
- 프론트엔드: React
- 백엔드: FastAPI
- DB: PostgreSQL
- UI 도구: Figma
- 테스트 방식: 로컬 `.venv` 가상환경에서 실행 (구체적 테스트 프레임워크는 미정)
- 시연·배포 환경: Vercel

## 선택 이유 (팀 경험·기간·핵심 기능으로)
1. Python(FastAPI)이 해외에서 널리 쓰여 참고할 자료와 레퍼런스가 많다
2. 코드 가독성이 좋아 팀원 간 공유·협업이 쉽다
3. OCR·LLM 연동(F-03 판독)에 쓸 라이브러리와 예제가 Python 쪽에 많아 핵심 기능 구현이 더 쉽다

## 선택하지 않은 안과 이유
- A안(React + Spring Boot): 위 세 가지 기준(해외 사용 빈도, 가독성, LLM 연동 편의성)에서 B안보다 불리하다고 판단해 선택하지 않았다

## LLM 연결
> 우리 서비스에서 LLM이 맡는 일(초안·요약·분류·설명)을 어느 스택에서 호출하는지, 상태를 바꾸는 최종 결정은 어디서 하는지 한 줄로 씁니다.
- FastAPI 백엔드가 OCR 판독 결과·발주 내용·상품 목록을 LLM에 보내 공통 JSON 정리와 품목 후보 매칭을 받는다 (03-rules-states-llm.md 3-4 L1). 재고 반영 여부는 LLM이 정하지 않고, 직원 확정(일반 건) 또는 사장님 승인(예외 건) 뒤 FastAPI가 시스템 규칙으로 반영한다 (R3, 3-2).

## 예상 어려움과 대응
| 어려움 | 대응 |
| --- | --- |
| Vercel은 서버리스 환경이라 실행 시간 제한이 있어, OCR+LLM 판독처럼 시간이 걸리는 작업이 시간 초과로 실패할 수 있다 | 판독처럼 오래 걸리는 작업은 별도 큐·워커로 분리하거나, 실행 시간 제한이 없는 호스팅(예: Railway, Render)을 함께 검토한다 |
| React ↔ FastAPI 사이 업로드 → 판독 비동기 처리 구조가 처음이다 (client-meeting-1 피드백 11) | 첫 데모 범위에서는 단순 폴링(polling) 방식으로 먼저 동작시키고, 필요하면 이후에 큐·웹소켓으로 바꾼다 |
| 온디바이스 마스킹(직원 기기 안에서 거래처 담당자 정보 가리기)의 구현 방식이 아직 정해지지 않았다 (03-rules-states-llm.md 3-4) | 뼈대 단계에서는 서버 쪽에서 임시로 마스킹 처리하고, 실제 기기 내 구현 방식은 이후 비교해 정한다 |
