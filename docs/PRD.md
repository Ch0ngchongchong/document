## 1. 개요
> 가져올 곳: 제안서(v2) 요약

- 프로젝트명: 딱 재고
- 목적 (한 줄): 거래명세서 사진·PDF를 OCR+LLM으로 읽어 상품명·수량·단가를 표로 정리하고 발주 내용과 다른 줄을 표시해, 직원이 실물과 대조·확정하고 필요하면 사장님 승인을 거쳐 재고에 반영한다. 명세서 한 장 처리 시간(현재 약 7분)을 절반 이하로 줄이는 것이 목표다. (proposal/draft.md 제안 요약)
- 사용자 (한 줄): 소규모 카페의 매장 직원(명세서 업로드·대조·확정)과 매장 사장님(발주 작성·승인, 예외 건 승인·반려). 평균 연령 약 47세. 테스트 범위는 카페 1곳, 관리 품목 약 150개, 거래처 5곳(식자재 2·유제품 1·원두 1·포장재 1). (proposal/draft.md, client-meeting-1)
- 개발 기간: 8주, 첫 데모는 3주차 (mvp-scope.md "8주 안에 반드시 동작", user-flows.md). 남은 수업일 × 시간은 미정 (stack-inputs.md 미기록)

> 가져올 곳: `docs/STACK.md`. 다르게 쓰지 않습니다.

## 7. 상태와 LLM의 역할
> 가져올 곳: `03-rules-states-llm.md`. **사람이 확인하기 전에는 상태가 바뀌지 않는다**와 **LLM에 보내지 않을 정보**를 그대로 옮깁니다.

- 상태 전이 (핵심 대상: 입고 검수 건, 03 3-2):
  - (시작) → 업로드 대기: 시스템 — 연결된 발주 건이 `입고 대기`가 된다
  - 업로드 대기 → 판독 중: 매장 직원 — 거래명세서 사진·PDF를 올린다
  - 판독 중 → 직원 확인 대기: 시스템(OCR+LLM) — 공통 JSON으로 정리·품목 후보를 붙이고, 발주와 다른 줄·불확실한 값을 표시한다
  - 판독 중 → 업로드 대기: 시스템 — 판독 실패, 다시 올려 달라고 알린다
  - 직원 확인 대기 → 재고 반영 완료: 직원 확정 → 시스템 반영 — 일반 건(발주와 모두 같음). 되돌릴 수 없음
  - 직원 확인 대기 → 사장 승인 대기: 직원 확정 → 시스템 분류 — 예외 건(수량 차이·파손·단가 변경·발주에 없는 품목). 재고는 아직 안 바뀜
  - 사장 승인 대기 → 직원 확인 대기: 직원 — 사장님 처리 전 확정 취소
  - 사장 승인 대기 → 승인 → 재고 반영 완료: 사장님 승인 → 시스템이 승인된 수량·단가로 반영, 모자란 수량은 발주 건에 미입고로 남김
  - 사장 승인 대기 → 반려: 사장님 — 반려 사유 입력, 재고는 안 바뀜
  - 반려 → 직원 확인 대기: 직원 재검수 / 반려 → 검수 종료(끝): 사장님이 공급처에 반품·정정 요청 후 닫음
  - 발주 건: 발주 초안 → 발주 확인 완료 → 공급처 전달 완료 → 입고 대기 (→ 입고 검수 건 `재고 반영 완료` 시 입고 완료) / 발주 초안 → 발주 취소(끝) (backlog US-01·US-02)
- LLM이 맡는 일 (03 3-4 L1): LLM은 문자를 읽지 않는다(OCR이 읽음). ① 공급처마다 다른 명세서 서식을 공통 JSON 필드로 정리 ② 명세서 상품명을 우리 상품 목록과 비교해 품목 후보(최대 3개)와 고른 이유 제시. 확신하지 못한 값은 추측해서 채우지 않고 `uncertain_fields`에 적는다. 후보가 없으면 빈 배열로 두고 새 상품을 만들지 않는다.
- 상태를 바꾸는 결정을 하는 곳 (규칙 / 사람):
  - **LLM은 재고를 직접 바꾸지 않는다.** LLM 출력은 `직원 확인 대기` 화면의 초안일 뿐이며, 재고는 직원 확정(일반 건) 또는 사장님 승인(예외 건) 뒤에 시스템이 바꾼다.
  - 일반 건·예외 건 분류는 직원 확정 시 시스템이 발주 내용과 비교해 규칙으로 나눈다.
  - LLM `uncertain_fields`, 규칙 검증 실패(수량 × 단가 ≠ 금액, 줄 금액 합 ≠ 합계, OCR 글자에 없는 숫자가 JSON에 있음), 품목 후보 없음 또는 비슷한 후보 2개는 강조되고 직원이 직접 입력하거나 확인해야 확정할 수 있다.
- LLM에 보내지 않을 정보: 명세서에 적힌 거래처 담당자 이름·연락처, 사업자 정보 → 직원 기기(휴대폰) 안에서 가린 뒤, 공통 JSON에 필요한 데이터만 뽑아 외부로 보낸다. 원본 사진은 외부 LLM에 보내지 않는다 (온디바이스 마스킹). 공급처 이름·사업자 정보는 발주 건에 이미 있으므로 JSON 필드에 넣지 않는다.

## 10. MVP 범위와 제외
> 가져올 곳: `docs/decisions/mvp-scope.md`. 포함은 이유와 함께 옮기고, 제외는 항목명만 두고 자세한 이유는 `mvp-scope.md`를 가리킵니다 (prd-review.md 2번, 2026-11-02 반영).

- MVP 포함 (8주 안에 반드시 동작 — 필수 스토리 전부, 취소·반려 스토리 포함):
  - US-01 발주 작성·승인·전달 (F-02): 입고 검수의 비교 기준이 되는 발주가 있어야 명세서와 대조할 수 있다. 발주량 초과 판정도 발주가 있어야 가능하다
  - US-02 공급처 전달 전 발주 취소 (F-02, 취소·반려): 잘못 만든 발주가 입고 대기로 넘어가지 않게 막는 예외 경로다
  - US-03 거래명세서 업로드·판독 (F-03): 핵심 가치이면서 가장 불확실한 부분이다 (client-meeting-1 피드백 1)
  - US-04 발주·납품 대조 및 일반 건 확정 (F-04): 직원이 확정하기 전에는 재고가 바뀌지 않는다는 첫 데모의 핵심 규칙이다 (03 R3)
  - US-05 단위 환산 및 수량 검증 (F-05): 박스·낱개 혼동이 가장 흔한 입력 오류다 (인터뷰 답변 3)
  - US-06 예외 건 사장 승인·반려 (F-06, 취소·반려): 초과 입고·높은 단가·미등록 상품은 직원이 혼자 확정하면 안 된다 (인터뷰 답변 4). 반려 경로를 포함한다
  - US-07 입고 변경 이력 조회 (F-07): 누가 무엇을 바꿨는지 되짚어야 하고, 정확도·비용을 측정하는 근거가 된다 (피드백 8, 9)
  - US-08 상품·단위 정보 등록 (F-01): 품목 매칭과 단위 환산의 기준 데이터다. 없으면 US-03~US-05가 동작하지 않는다
- 이번에 제외 (자세한 이유는 `docs/decisions/mvp-scope.md` 참고):
  - 판매량 예측·발주 수량 추천
  - POS 연동으로 판매 시 재고 자동 차감
  - 공급처 자동 발주 전송(문자·앱)과 공급처 취소 승인·거절
  - 반려 뒤 공급처 반품·재납품 처리
  - POS 실연동 (F-08, 선택)
  - 고객 요청이었으나 제외: POS 연동
- 시연용 단순화와 제약:
  - 첫 데모(3주차)는 user-flows.md의 일반 건 흐름 1개만 보여 준다 (업로드 대기 → 판독 중 → 직원 확인 대기 → 재고 반영 완료). 예외 건 사장 승인(US-06)은 데모 흐름에 넣지 않았으며, 5-1 MVP 가설 흐름에는 사장 승인 단계가 있어 팀 확인이 필요하다 (mvp-scope.md)
  - 공급처 전달은 사장님이 '전달 완료'를 직접 표시한다
  - POS는 모의 연동용 데이터 형식만 준비한다
  - 판독 비동기 처리는 첫 데모에서 단순 폴링으로 먼저 동작시킨다. 온디바이스 마스킹은 뼈대 단계에서 서버 쪽 임시 마스킹으로 처리하고 실제 기기 내 구현은 이후 정한다 (STACK.md 예상 어려움과 대응)
