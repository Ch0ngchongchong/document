# 5. MVP 가설, 기능 목록, 가정·위험, 클라이언트 질문지, 미팅 준비

> 목표: 우리가 만들 것과 모르는 것을 목록으로 만들고, 모르는 것을 클라이언트가 답할 수 있는 질문으로 바꾼다.

## 5-1. MVP 가설

> 클라이언트 미팅 전 우리의 추측입니다. 미팅 뒤 바뀔 수 있습니다. 제안서 Ⅰ-3 제안 범위, Ⅳ-10 목표 흐름의 바탕이 됩니다.

| 구분 | 내용 |
| --- | --- |
| 핵심 사용자 흐름 1개 (첫 데모에서 보여 줄 것) | 입고 검수 건 하나가 처음부터 끝까지 가는 흐름 (3-2). ① **명세서 업로드**: 물건이 오면 직원이 거래명세서 사진·PDF를 올린다 (업로드 대기 → 판독 중) ② **판독**: OCR이 글자를 읽고 LLM이 공통 JSON 필드로 정리한 뒤 품목 후보를 붙인다. 시스템이 발주와 다른 줄과 불확실한 값을 표시한다 (→ 직원 확인 대기) ③ **직원 검수**: 직원이 실물과 대조해 고친 뒤 확정한다. 발주와 모두 같으면 일반 건, 하나라도 다르면 예외 건이 된다 ④ **예외 사장 승인**: 예외 건은 사장님이 사유를 보고 승인하거나 반려한다 (→ 사장 승인 대기 → 승인 / 반려) ⑤ **재고 반영**: 일반 건은 직원 확정 뒤, 예외 건은 사장님 승인 뒤 시스템이 재고에 더한다 (→ 재고 반영 완료). 되돌림 경로: 판독 실패 → 다시 업로드, 반려 → 직원 재검수. 비교 기준이 되는 발주 건은 사장님이 미리 입력해 둔다. 근거: 3-2 상태 전이, 4-1 후보 A |
| 이 흐름에서 LLM이 쓰이는 곳 | ② 판독 단계만. 글자 읽기는 OCR이 하고, LLM은 공급처마다 다른 서식을 공통 JSON 필드로 정리하고 품목 후보를 매칭하는 일만 한다 (3-4 L1). LLM은 재고를 바꾸지 않는다. 확신이 없는 값과 규칙 검증에 실패한 값은 직원이 직접 확인해야 확정할 수 있다. 거래처 담당자 이름·연락처는 직원 기기 안에서 가린 뒤 필요한 데이터만 LLM에 보낸다 (온디바이스 마스킹, 5-4) |
| MVP 테스트 범위 (이번에 확인할 것) | **카페 1곳, 약 150개 품목, 거래처 5곳**으로 제한한다. 이 범위에서 실제 명세서로 ①~⑤ 흐름이 도는지, 직원이 고쳐야 하는 칸이 얼마나 되는지, 예외 건이 얼마나 나오는지 확인한다. 거래처 5곳의 명세서 서식이 몇 가지인지도 함께 확인한다 (3-4 OCR+규칙 비교의 확인 필요 항목). 품목 수와 거래처 수는 미팅에서 실제 숫자로 고친다 [가정] |
| 확장 목표 (이번 MVP에서 확인하지 않음) | 매장 여러 곳, 업종이 다른 가게(식당·편의점 등), 품목 수백~수천 개, 처음 보는 거래처 서식. MVP 결과가 좋아도 이 범위에서 똑같이 된다고 말하지 않는다. 특히 품목 수가 늘면 비슷한 상품명이 많아져 품목 매칭이 어려워질 수 있다 [추정] |
| 당장 제외할 것과 이유 | ① 판매량 예측·발주 수량 추천 (3-4 L2, 후보 C): 판매 기록이 쌓여야 하고 예측이 맞는지 첫 데모 안에 확인하기 어렵다. 발주 수량은 사장님이 직접 넣는다 ② POS 연동으로 판매 시 재고 자동 차감 (후보 B): 외부 POS마다 연동 방식이 달라 시간이 오래 걸린다 ③ 공급처에 문자·앱으로 자동 발주 전송과 발주 취소 흐름: 공급처마다 주문 방식이 다르다 (2-2 순서 5). 발주는 비교 기준으로만 입력한다 ④ 반려 뒤 공급처 반품·재납품 처리 (3-1 R4): 공급처 화면까지 필요하다. MVP에서는 반려 사유를 남기고 검수 건을 닫는 데까지만 한다. 부분 입고는 예외 건으로 사장님이 승인하는 방식으로 처리한다 |

## 5-2. 주요 기능 목록

> 5~8개. '필수'는 첫 데모에 꼭 있어야 하는 기능, '선택'은 시간이 되면 만드는 기능입니다. 제안서 Ⅳ-11의 바탕이 됩니다.

| ID | 기능명 | 설명 | 사용자 | 우선순위 (필수/선택) | 관련 상태 전이 / LLM |
| --- | --- | --- | --- | --- | --- |
| F-01 | 상품·단위 정보 관리 | 상품 코드·상품명·규격·기준 재고 단위·포장 단위·환산값·기준 단가를 등록하고 수정한다. 거래명세서의 품목을 기존 상품과 맞추는 기준 데이터로 사용한다. | 매장 사장님, 직원 | 필수 | 상태 전이 없음. 상품 매칭과 단위 환산의 기준 데이터 |
| F-02 | 발주 작성·승인·취소 | 상품과 수량을 골라 발주를 작성하고 승인한다. 공급처에 보낸 뒤 '전달 완료'로 표시하며, 보내기 전에는 취소할 수 있다. | 매장 사장님 | 필수 | 발주 초안 → 발주 확인 완료 → 공급처 전달 완료 → 입고 대기 / 발주 초안 → 발주 취소 |
| F-03 | 거래명세서 업로드·판독 | 거래명세서 사진·PDF를 올리면 품목 코드·상품명·규격·수량·단위·단가·금액 등을 공통 형식의 표로 정리한다. 기존 상품 목록에서 품목 후보를 찾고, 판독이 불확실한 값은 별도로 표시한다. 거래처 담당자 이름·연락처 등 불필요한 개인정보는 직원 기기 안에서 가린 뒤 필요한 데이터만 외부 LLM으로 보낸다 (온디바이스 마스킹, 5-4). | 매장 직원 | 필수 | 입고 대기 → 판독 중 → 직원 확인 대기 / OCR·LLM 판독 |
| F-04 | 발주·납품 대조 및 직원 검수 | 판독 결과와 발주 내용을 나란히 보여 주고 품목·수량·단가가 다른 행을 표시한다. 직원은 실제 입고된 상품과 대조하고 잘못 읽힌 값을 수정한 뒤 검수를 완료한다. 직원 검수와 필요한 예외 승인이 끝나기 전에는 재고를 변경하지 않는다. | 매장 직원 | 필수 | 판독 중 → 직원 확인 대기 → 재고 반영 완료 또는 예외 승인 대기 |
| F-05 | 단위 환산 및 수량 검증 | 박스·묶음·낱개 등 거래명세서의 단위를 기준 재고 단위로 환산한다. 상품별 환산값이 등록되어 있지 않거나 단위가 불분명하면 자동 처리하지 않고 직원 확인 대상으로 표시한다. | 매장 직원 | 필수 | F-01의 단위 정보와 F-03의 판독 결과 활용. 환산은 등록된 규칙으로 처리 |
| F-06 | 예외 판정 및 사장 승인 | 발주량 초과, 기준을 넘는 단가, 미등록 상품, 불확실한 품목 매칭 등의 예외를 표시하고 사장님에게 승인을 요청한다. 사장님은 예외 내용을 확인해 승인하거나 반려한다. 구체적인 판정 기준은 클라이언트 확인 후 정한다. | 매장 사장님 | 필수 | 직원 확인 대기 → 예외 승인 대기 → 승인 또는 반려 → 재고 반영 여부 결정 |
| F-07 | 입고 변경 이력 관리 | 판독 원본값, 직원 수정값, 검수 결과, 사장 승인·반려 결과, 최종 재고 반영 수량과 처리 시각을 기록한다. 누가 어떤 값을 변경했는지 확인할 수 있도록 한다. 판독 건마다 LLM 호출 비용·처리 시간도 함께 남겨, 판독 원본값과 직원 수정값의 차이로 정확도와 비용 절감 효과를 꾸준히 측정한다 (03 3-4 측정과 기록). | 매장 사장님, 직원 | 필수 | 판독·수정·검수·승인·재고 반영 과정의 변경 이력 |
| F-08 | POS 연동 또는 모의 연동 | 실제 POS의 제품명과 API·데이터 내보내기 지원 여부를 확인한다. 실연동이 가능하면 연동 범위를 검토하고, 확인 전에는 테스트용 데이터를 이용한 모의 연동을 우선한다. | 매장 사장님, 개발팀 | 선택 | POS와 재고 데이터의 연동. 실제 POS 및 연동 방식 확인 후 범위 결정 |

> 초기 테스트 범위는 카페 1곳, 약 150개 품목, 거래처 5곳으로 제한합니다. 이는 초기 테스트 대상이며, 전체 서비스의 지원 범위나 향후 확장 목표와는 구분합니다.
> 사장님이 쓰는 화면(F-02 발주 승인, F-06 예외 승인)은 인터뷰로 확인된 주 사용자 평균 연령대(약 47세)에 맞춰 글자·버튼 크기를 크게 하고 조작 단계를 단순화합니다 (client-meeting-1 피드백 12번).

## 5-4. 위험 요소

> 2~3개 이상의 주요 위험을 정리합니다. 제안서 Ⅶ-17의 바탕이 됩니다. 아래 대응은 구현 및 검증이 필요한 계획이며, 이미 보장된 기능을 의미하지 않습니다.

| 위험 | 일어나면 생기는 일 | 대응 |
| --- | --- | --- |
| LLM·OCR이 거래명세서를 잘못 읽는다: 수량·단가를 오인식하거나 행을 누락하고, 상품명을 다른 상품과 매칭한다. | 납품 수량·매입 단가·재고가 잘못 기록되고, 발주와 입고의 차이를 놓칠 수 있다. | OCR+규칙 방식과 OCR+LLM 방식을 같은 테스트 자료로 비교한다. 필드별 정확도, 행 누락률, 직원 수정률을 측정한다. 직원이 실물과 대조해 확정하기 전에는 재고를 변경하지 않는다. 불확실한 값과 상품 매칭은 자동 확정하지 않고 직원이 직접 수정·선택하도록 한다. 판독에 실패하면 직접 입력으로 전환한다. |
| 단위 환산 오류: 박스·묶음·낱개가 혼동되거나 환산값이 잘못 등록된다. | 실제보다 많은 수량 또는 적은 수량이 재고에 반영된다. | 상품별 기준 재고 단위와 환산값을 등록하고, 등록된 규칙으로만 환산한다. 환산값이 없거나 단위가 불명확하면 자동 처리하지 않고 직원 확인 대상으로 보낸다. 단위 혼동 사례를 별도 테스트한다. |
| 상품 오매칭: 상품명이나 규격이 비슷한 다른 상품을 선택한다. | 잘못된 상품의 재고가 증가하고 이후 발주 판단에도 오류가 생길 수 있다. | 상품 코드·규격·단위 등 확인 가능한 정보를 함께 비교한다. 후보가 여러 개이거나 일치 여부가 불확실하면 직원이 직접 선택하게 한다. 미등록 상품을 임의로 기존 상품에 연결하지 않는다. |
| 예외 판정 기준이 불명확하다: 발주량 초과나 단가 차이를 어느 수준부터 예외로 볼지 정해지지 않았다. | 정상 입고가 불필요하게 지연되거나 확인이 필요한 예외가 일반 입고로 처리될 수 있다. | 발주량 초과, 단가 허용 차이, 미등록 상품 등의 기준을 클라이언트에게 확인한다. 기준이 정해지지 않은 항목은 `[가정]`으로 관리하고, 불확실한 예외는 사장 승인 대상으로 보낸다. |
| 개인정보·거래처 정보가 외부 LLM 서비스로 전송된다: 담당자 이름·연락처 등 불필요한 정보가 마스킹되지 않는다. | 거래처 담당자의 개인정보 등 불필요한 정보가 외부 서비스로 전달될 수 있다. | **온디바이스 마스킹**: 명세서를 찍은 직원 기기(휴대폰) 안에서 이름·연락처·사업자 정보 등 민감 정보를 가린 뒤, 공통 JSON 필드(3-4 L1)에 필요한 데이터만 뽑아 외부로 보낸다. 원본 사진은 외부 LLM에 보내지 않는다. 기기에서 가릴 영역을 찾지 못하거나 마스킹에 실패하면 자동 전송하지 않고 직원 확인 대상으로 돌린다. 기기 안에서 OCR까지 할지, 사진에서 영역만 가릴지와 기기 성능에 따른 처리 시간은 구현 방식을 비교한 뒤 정한다 [가정]. 실제 전송 범위, 저장 위치, 보관 기간은 사용할 서비스의 정책을 확인한 뒤 확정한다. |
| POS와 입고 서비스의 재고가 일치하지 않는다. | 재고가 중복 반영되거나 POS 재고와 입고 서비스의 재고가 달라질 수 있다. | POS 제품명, API·데이터 내보내기 지원 여부, 기준 재고 시스템을 먼저 확인한다. 실제 연동 전에는 테스트 데이터를 이용해 모의 검증한다. 실연동 시 중복 반영 방지와 오류 발생 시 재처리 절차를 설계한다. |
| 동시 업로드나 판독 요청으로 처리 지연이 발생한다. | 마감 후 업무가 몰릴 때 직원의 대기 시간이 늘어나고 입고 처리가 늦어질 수 있다. | 클라이언트에게 동시 사용 규모와 마감 후 처리량을 확인한다. 업로드별 처리 상태를 표시하고 중복 제출 방지 방안을 검토한다. 성능 테스트 전에는 처리 시간을 보장하지 않으며, 지연이나 실패 시 재시도 또는 직접 입력 절차를 마련한다. |
| 기능 범위가 커져 8주 안에 핵심 흐름을 완성하지 못한다. | 발주부터 판독·검수·재고 반영까지 이어지는 필수 기능이 첫 데모에서 빠질 수 있다. | F-01~F-07의 핵심 흐름을 우선 구현하고, 클라이언트가 제공한 대표 거래명세서 양식으로 먼저 테스트한다. 부분 입고·반품과 POS 실연동은 핵심 흐름 검증 이후 결정한다. 일정이 부족하면 선택 기능과 추가 양식 지원을 제외한다. |

## 5-5. 클라이언트 질문지

> 카테고리마다 1개 이상, 총 8~10개. 미팅 질문 시간은 팀당 약 12분이므로 우선순위 1~5번은 반드시 묻는 질문입니다. **1~3번은 제안서 Ⅶ-18에 넣어 미리 보냅니다.** 질문을 고칠 때 팀원끼리 서로 읽어 보고 예/아니오로 끝나거나 답을 유도하는 질문을 고칩니다.
>
> 좋은 질문의 조건: ① 예/아니오로 끝나지 않는다 ② 구체적인 사례를 들어 묻는다 ③ 우리 해결책을 정답으로 유도하지 않는다 ④ 답을 들으면 무엇을 결정할지 알고 있다.

| 우선순위 | 구분 | 질문 | 관련 가정 | 답변에 따른 결정 |
|---|---|---|---|---|
| 1 | 목적·성과 기준 | 현재 거래명세서를 재고에 등록하는 과정에서 가장 불편한 점은 무엇인가요? | 거래명세서 수기 입력이 주요 문제이다. | 핵심 해결 문제 확정 |
| 2 | 목적·성과 기준 | 거래명세서 한 건을 확인하고 입력하는 데 평균적으로 얼마나 걸리나요? | 입력 시간 단축이 의미 있는 효과를 낸다. | 목표 처리 시간 설정 |
| 3 | 규칙 | 거래명세서의 품목과 수량을 발주 내용과 대조하는 과정에서 오류가 자주 발생하나요? | 발주 내용과 입고 내역의 대조가 필요하다. | 대조 기능의 필요성 확정 |
| 4 | 사용자·권한 | 물건 입고 확인과 재고 등록은 주로 누가 담당하나요? | 사장님이나 직원이 입고를 확인한다. | 사용자 권한 및 역할 설정 |
| 5 | 규칙 | 거래명세서의 품목명이 실제 재고에 등록된 상품명과 다른 경우가 있나요? | 품목명 불일치가 발생할 수 있다. | 상품명 매칭 기능 범위 결정 |
| 6 | 예외 처리 | 주문한 수량보다 적거나 많은 물건이 도착하면 현재 어떻게 처리하나요? | 입고 수량과 주문 수량이 다를 수 있다. | 예외 처리 기능 우선순위 결정 |
| 7 | LLM 활용 | 거래명세서를 AI가 판독한 뒤 직원이 결과를 확인하고 입고를 확정하는 방식이 적절한가요? | AI 판독 결과에 대한 사람의 확인이 필요하다. | 입고 확정 절차 결정 |
| 8 | 데이터·연동 | 거래명세서는 주로 종이 사진, PDF, 엑셀 중 어떤 형태로 받나요? | 이미지나 PDF에서 정보를 추출할 수 있다. | 지원 파일 형식 결정 |
| 9 | 데이터·보안 | 거래명세서에 개인정보나 외부 AI에 전달하면 안 되는 정보가 포함되나요? | 개인정보를 마스킹해야 할 수 있다. | 데이터 마스킹 및 처리 정책 결정 |
| 10 | 범위·우선순위 | 첫 버전에서 반드시 필요한 기능과 나중에 추가해도 되는 기능은 무엇인가요? | 거래명세서 판독과 입고 확인만으로도 핵심 가치를 제공할 수 있다. | MVP 범위 최종 확정 |
| 11 | 규칙 | 거래명세서에는 '박스'로 오지만 재고는 '개'로 세는 상품이 있다면, 예를 들어 어떤 상품이 한 박스에 몇 개인가요? 그 환산은 지금 어디에 적어 두고 누가 맞추나요? | 명세서 단위와 재고 단위가 다를 수 있고, 상품마다 포장 환산 값이 정해져 있다. | F-01에 기준 재고 단위·포장 환산 항목 추가 여부, F-04에서 환산해 재고에 더하는 방식 결정 |
| 12 | 규칙 | 명세서의 단가를 보고 '평소보다 비싸다'고 느끼는 기준은 무엇인가요? 최근 그런 적이 있었다면 얼마나 차이 났고, 그때 어떻게 처리했나요? | 등록한 매입 단가와 비교해 차이가 크면 이상 단가로 본다. | F-04에서 단가를 강조할 기준값(금액·비율)과 강조 뒤 처리 방법 결정 |
| 13 | 사용자·권한 | 직원이 사장님께 묻지 않고 입고를 끝내도 되는 경우와 꼭 사장님 확인을 받아야 하는 경우를 각각 예를 들어 주실 수 있나요? | 발주 승인은 사장님이, 입고 확정은 직원이 한다. | 역할별 권한, 입고 확정 뒤 사장님 승인 단계 추가 여부 결정 |
| 14 | 데이터·연동 | 지금 쓰시는 POS는 어떤 제품이고, 상품 목록이나 판매 내역을 어떤 방법(엑셀 내보내기, 연동 기능 등)으로 꺼낼 수 있나요? | POS 연동 없이 상품 목록을 따로 등록해도 첫 데모를 쓸 수 있다. | F-01 상품 목록 가져오기 방식, POS 연동을 첫 데모에서 계속 뺄지 결정 |
| 15 | 운영·규모 | 물건이 가장 많이 들어오는 날을 예로 들면, 마감 후 거래명세서를 몇 장(몇 줄) 처리하고, 그때 몇 명이 동시에 입력하나요? | 하루 처리량이 많지 않고 한두 명이 나눠 입력한다. | 판독 대기 시간 목표, 여러 명이 같은 입고를 고칠 때의 충돌 처리 필요 여부 결정 |
| 16 | 사용 환경 | 입고를 확인할 때 휴대폰, 태블릿, 카운터 PC 중 무엇으로 하시나요? 명세서 사진은 어떤 기기로 찍나요? | 직원이 휴대폰으로 사진을 찍고 같은 화면에서 대조한다. | 주 대상 화면 크기, F-04 대조 화면 배치(나란히 보기 / 줄 단위 카드) 결정 |

> 질문지를 Claude에게 보여 주고 '빠진 관점'을 물어본 결과는 [ai-check-log.md](../domain/ai-check-log.md#질문지-검토-5단계)에 적습니다.

## 5-6. 미팅 역할 분담

> 미팅 진행 역할과 미팅 뒤 피드백 실행 책임을 구분한다. 각 실행 영역에는 최종 정리 담당자 1명을 두고, 다른 팀원은 필요한 자료를 함께 확인한다. 아래 배정은 사전활동의 고객 피드백 정리 역할이며 스프린트별 개발 역할은 [팀 역할](../team/roles.md)을 따른다.

### 미팅 당일 역할

| 역할 | 하는 일 | 담당 |
| --- | --- | --- |
| 진행자 | 우선순위 1~5 질문을 먼저 묻고 답변에 따라 후속 질문을 선택한다. 질문 시간이 한 주제에 쏠리지 않게 조정하고, 결정이 필요한 쟁점을 분명히 한다. | 신은총 |
| 기록자 | 답변을 추측이나 해석과 분리해 기록한다. 숫자·단위·사례·담당자 이름은 가능한 한 그대로 적고, 확인하지 못한 값은 미확인으로 표시한다. 질문 번호가 연결된 회의록을 만든다. | 김가은 |
| 꼬리 질문자 | "최근 사례를 하나 들어 주실 수 있나요?", "그때 누가 어떤 순서로 처리했나요?"라고 물어 실제 업무와 예외를 확인한다. 현행 업무 순서와 명세서·품목·단위 사례를 기록자에게 전달한다. | 진수화 |
| 시간·가정 체커 | 남은 시간을 알리고, 답변이 기존 가정과 일치하는지·반대되는지 표시한다. 새 가정과 미답변 질문도 따로 적어 확인·수정·미확인 목록을 만든다. | 권기범 |
| 요약·확인자 | 종료 전에 핵심 결정, 남은 질문, 다음 조치를 짧게 되읽고 고객에게 이해가 맞는지 확인한다. 고객 확인 요약과 후속 확인 항목을 기록자에게 전달한다. | 김지운 |

### 미팅 후 실행 책임

> 담당자는 표의 산출물을 정리해 팀에 공유한다. 고객 답변으로 확정되지 않은 기준은 임의로 결정하지 않고 `[가정]` 또는 미결정으로 남긴다. 괄호의 질문 번호는 5-5와 연결한다.

| 영역 | 맡는 피드백 (관련 질문) | 담당 | 산출물 |
| --- | --- | --- | --- |

### 담당자 간 인수 기준

- 명세서·단위 담당자는 판독 검증 담당자에게 익명화 샘플과 사람이 확인한 정답표를 전달한다.
- POS 담당자는 POS 연동 가능 여부와 기준 재고 시스템을 확인해 UX·테스트 및 고객 요구사항 담당자에게 공유한다.
- 판독 검증 담당자는 샘플별 비교 결과와 오류 사례를 공유한다. 정확도·비용 기준이 정해지기 전에는 특정 방식이 더 낫다고 결론 내리지 않는다.
- UX·테스트 담당자는 확인된 권한·예외 규칙만 화면과 시나리오에 반영한다. 확인되지 않은 기준은 미결정으로 표시한다.
- 고객 요구사항 담당자는 각 결과물을 취합하고, 상충하는 결정은 팀 합의 안건으로 남긴다.
