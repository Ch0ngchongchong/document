# 우리 팀의 첫 기능

> **저장 위치:** `docs/decisions/first-feature.md`

> **사용 방법**
> 1. 2-2에서 만든 뼈대 위에 **기능 하나**를 끝까지 만듭니다. 어떤 기능인지는 **팀이 고릅니다.** Claude가 정해 주지 않습니다. Claude는 후보의 빈틈을 찾아 줄 수만 있습니다.
> 2. 기능은 `backlog.md`의 **필수 스토리 하나**입니다. 인수 조건에 `미정`이 없고, 화면·서버·데이터를 **모두 거치고**, 오늘 안에 끝낼 수 있게 작은 것을 고릅니다. LLM 호출이 들어간 기능은 오늘은 피합니다(키와 실패 시 동작까지 정해야 해서 범위가 커집니다).
> 3. 이 파일은 **PM이** 팀 결정을 받아 적습니다. 2절 셋째 칸 (테스트할 내용)은 **테스트 담당이 구현 전에** 적습니다. 입력과 기대 결과는 인수 조건과 `../../../3주차 1일차 배포 파일/API.md`에 적힌 것만 씁니다. 같은 파일을 동시에 고치지 않습니다. 후보 비교는 팀 채팅의 후보 표로 하고 여기에는 고른 이유만 적습니다. 승인한 계획의 영역별 할 일도 문서에 옮겨 적지 않고 PM이 팀 채팅에 올립니다.
> 4. 2절의 완성 기준은 **`backlog.md`의 인수 조건에서 가져옵니다.** 새로 만들지 않습니다. 정하지 않은 규칙은 `미정`으로 남깁니다.
> 5. `>`로 시작하는 안내 문장은 지워도 됩니다.

- 작성일:
- 고른 스토리: `US-08` (기능 ID `F-01`)

- 고른 이유 (우리 팀 상황에서):
- 고르지 않은 후보와 이유 (다음 시간 이후에 다시 볼 것):

## 2. 완성 기준 (인수 조건에서 가져옴)

| # | 인수 조건 (`backlog.md` 원문) | 오늘 만드나 | 테스트할 내용 (입력 → 기대 결과, 인수 조건·`../../../3주차 1일차 배포 파일/API.md`에 적힌 것만) / 확인 방법 |
| --- | --- | --- | --- |
| 1 | (정상) 사장님이 상품 코드·상품명·규격·기준 재고 단위·포장 단위·환산값·기준 단가를 입력해 저장하면 상품 목록에 추가되고, 이후 판독의 품목 후보 대상이 된다 | 예 (상품 등록·목록 확인); 판독 후보 확인은 이후 | 사장님이 해당 정보를 입력해 저장 → 상품 목록에 추가되는지 화면에서 확인. 판독 시 품목 후보 대상이 되는지는 판독 기능 구현 후 확인 |
| 2 | (정상) 환산값이나 기준 단가를 수정하면 그 뒤에 확정하는 건부터 새 값이 적용되고, 이미 재고 반영 완료된 건의 수량·단가는 바뀌지 않는다 | 아니오 | 환산값 또는 기준 단가 수정 → 이후 확정 건에는 새 값이 적용되고 이미 재고 반영 완료된 건은 바뀌지 않는지 확인 |
| 3 | (실패·거절) 상품 코드가 중복되거나, 필수값이 비었거나, 환산값이 0 이하이면 저장되지 않는다 | 예 (중복 코드·환산값 0 이하); 필수값 누락은 결정 후 | 중복 상품 코드 또는 0 이하 환산값 입력 → 저장되지 않는지 확인. 필수값 범위는 미정이므로 결정 후 누락 입력을 확인 |
| 4 | (권한) 다른 매장 사용자는 이 매장의 상품 목록을 볼 수 없다 | 예 | 다른 매장 사용자로 상품 목록 조회 → 해당 매장 상품을 볼 수 없는지 확인 |
