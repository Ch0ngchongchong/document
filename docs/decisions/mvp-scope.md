## 포함 (8주 안에 반드시 동작 — 필수 스토리 전부, 취소·반려 스토리 포함)
| 스토리 | 기능 (F-__) | 왜 필수인가 |
| --- | --- | --- |
| US-01 발주 작성·승인·전달 | F-02 | 입고 검수의 비교 기준이 되는 발주가 있어야 명세서와 대조할 수 있다. 발주량 초과 판정도 발주가 있어야 가능하다 |
| US-02 공급처 전달 전 발주 취소 (취소·반려) | F-02 | 잘못 만든 발주가 입고 대기로 넘어가지 않게 막는 예외 경로다 |
| US-03 거래명세서 업로드·판독 | F-03 | 핵심 가치이면서 가장 불확실한 부분이다 (client-meeting-1 피드백 1) |
| US-04 발주·납품 대조 및 일반 건 확정 | F-04 | 직원이 확정하기 전에는 재고가 바뀌지 않는다는 첫 데모의 핵심 규칙이다 (03 R3) |
| US-05 단위 환산 및 수량 검증 | F-05 | 박스·낱개 혼동이 가장 흔한 입력 오류다 (인터뷰 답변 3) |
| US-06 예외 건 사장 승인·반려 (취소·반려) | F-06 | 초과 입고·높은 단가·미등록 상품은 직원이 혼자 확정하면 안 된다 (인터뷰 답변 4). 반려 경로를 포함한다 |
| US-07 입고 변경 이력 조회 | F-07 | 누가 무엇을 바꿨는지 되짚어야 하고, 정확도·비용을 측정하는 근거가 된다 (피드백 8, 9) |
| US-08 상품·단위 정보 등록 | F-01 | 품목 매칭과 단위 환산의 기준 데이터다. 없으면 US-03~US-05가 동작하지 않는다 |

## 제외 (이번에 만들지 않음)
| 제외 항목 | 왜 뺐는가 | 나중에 넣으면 영향 범위 |
| --- | --- | --- |
| 판매량 예측·발주 수량 추천 (03 3-4 L2, 후보 C) | 판매 기록이 쌓여야 하고, 첫 데모 안에서 예측이 맞는지 확인하기 어렵다. 발주 수량은 사장님이 직접 입력한다 | 판매 데이터 입력 경로가 필요하다. 발주 입력(US-01)에 추천값 표시, LLM 입력 범위 확대 |
| POS 연동으로 판매 시 재고 자동 차감 (후보 B) | 외부 POS마다 연동 방식이 달라 시간이 오래 걸린다. 실제 POS 제품과 API 여부를 아직 모른다 | 재고를 바꾸는 경로가 하나 더 생긴다. 재고 반영 규칙(US-04, US-06)과의 충돌을 다시 설계해야 한다. F-08 실연동 |
| 공급처 자동 발주 전송(문자·앱)과 공급처 취소 승인·거절 | 공급처마다 주문 방식이 다르다 (02 2-2 순서 5). MVP에서는 사장님이 '공급처 전달 완료'를 직접 표시하고, 발주는 비교 기준으로만 쓴다 | US-01의 수동 '전달 완료' 표시를 공급처 연동 상태로 바꾼다. 공급처 접수 상태를 추가한다. 사장님 내부 발주 취소(US-02)는 유지한다 |
| 반려 뒤 공급처 반품·재납품 처리 (03 3-1 R4) | 공급처 화면까지 필요하다. MVP는 반려 사유를 남기고 검수 건을 닫는 데까지만 한다 | US-06의 '검수 종료' 앞에 반품 단계와 공급처 화면을 추가한다. 반품 수량을 재고에서 빼는 규칙(R4)을 구현한다 |
| POS 실연동 (F-08, 선택) | 실제 POS 제품과 연동 방식을 확인하기 전이다 (client-meeting-1 질문 4, 피드백 10 반영 안 함) | 모의 연동용 데이터 형식만 MVP에서 준비한다. 확인 후 실연동 범위를 다시 정한다 |

## 첫 데모(3주차)에서 보여줄 것
(user-flows.md의 흐름과 같아야 함)

1. 시스템 — 발주 건이 입고 대기가 됨 (업로드 대기)
2. 직원 — 거래명세서 사진·PDF를 업로드함 (업로드 대기 → 판독 중)
3. 시스템(OCR+LLM) — 정리·매칭 완료, 다른 줄·불확실 값 표시 (판독 중 → 직원 확인 대기)
4. 직원 — 일반 건(발주와 모두 일치)을 확정함 (직원 확인 대기)
5. 시스템 — 확정된 수량·단가를 재고에 반영함 (재고 반영 완료)

> 예외 건의 사장 승인(US-06)은 이 데모 흐름에 넣지 않았습니다. 5-1 MVP 가설의 흐름에는 ④ 예외 사장 승인 단계가 있으므로 팀 확인이 필요합니다.

> `client-meeting-1.md`에서 '반영 안 함'으로 판정한 것 중 MVP와 관련된 것을 옮깁니다.

| 요청 | 제외 이유 | 다시 논의할 시점 |
| --- | --- | --- |
| POS 연동: 두 곳에서 따로 관리하면 값이 달라지므로 데이터는 한 곳에서만 관리 (피드백 10) | MVP에서는 하지 않고 향후 확장 과제로 남긴다 (5-1 제외 ②, 5-2 F-08 선택). MVP에서는 재고 데이터를 우리 시스템 한 곳에서만 관리해 값이 갈라지는 문제를 피한다 | 다음 미팅. POS 제품·API·데이터 내보내기 지원 여부를 확인한 뒤 F-08 범위를 다시 본다 |
