# AI 확인 기록

> Claude 등 AI에게 물어본 것 중 **확인해 보니 틀렸거나 애매했던 것**과, AI의 제안을 **채택하거나 버린 것**을 적습니다. 맨 아래에 이어서 씁니다.

## 물어보고 확인한 것 (1~3단계)

| 날짜 | 쓴 사람 | 물어본 내용 | AI 답변 요지 | 확인 결과와 출처 (카드 번호) |
| --- | --- | --- | --- | --- |
| 2026-10-13 | 본인 | 재고 관리 문제가 실제로 매장의 손실과 연결되는가? | 재고 관리가 제대로 이루어지지 않으면 결품이나 폐기 등의 문제가 발생할 수 있다. | 김성우(2019)의 「신선식품의 유통기한 입고 기준일을 고려한 재고 관리 방안에 대한 연구」에서 재고 관리 방안을 개선해 결품량과 폐기량을 줄인 사례를 확인했다. 다만 해당 연구는 신선식품 제조업체 사례이므로 소규모 매장의 거래명세서 수기 입력 문제를 직접 입증하지는 않는다. (관련 논문 자료, 카드 번호 확인 필요) |
| 2026-10-13 | 본인 | 기존 재고 관리 서비스가 있어도 새로운 입고 확인 서비스가 필요한가? | 기존 서비스에서도 입출고 기록과 재고 관리 기능을 제공하지만 거래명세서 판독 및 발주 내역 대조에 집중하는 서비스는 차별화 가능성이 있다. | 박스히어로 관련 자료를 통해 기존 재고 관리 기능을 확인했다. 그러나 기존 서비스에 거래명세서 자동 판독 기능이 없는지는 별도로 확인해야 하므로, 해당 기능이 없다고 단정하지 않고 입고 확인 과정의 차별성을 중심으로 기획하기로 했다. (1-shusbox-2, 5-shusbox-3) |
| 2026-10-13 | 본인 | AI가 거래명세서 사진에서 품목명과 수량을 정확하게 추출할 수 있는가? | OCR이나 멀티모달 AI를 이용하면 이미지에서 문자와 표 정보를 추출할 수 있으며, 추출 결과를 발주 내역과 비교하는 방식으로 활용할 수 있다. | 실제 거래명세서 양식별 판독 정확도는 아직 검증하지 않았다. 따라서 AI가 정확하게 처리한다고 단정하지 않고, 판독 결과를 사용자가 수정하고 확인한 뒤 입고를 확정하는 방식을 채택했다. (별도 검증 자료 없음, MVP 가정으로 기록) |

## 질문지 검토 (5단계)

> Claude에게 질문지를 보여 주고 '빠진 관점'을 물어봅니다. 제안을 그대로 넣지 말고, 채택한 것과 버린 것을 이유와 함께 적습니다.

| AI 제안 | 채택 / 보류 | 이유 |
| --- | --- | --- |
| 입고 확인에 걸리는 시간과 빈도(주당 거래명세서 장수, 1회 확인 시간)를 묻는 문항 추가 | 채택 | 김성우(2019) 연구는 신선식품 제조업체 사례라 소규모 매장 문제를 직접 입증하지 못한다. 매장 운영자에게 직접 수치를 받아야 문제의 크기를 확인할 수 있다. |
| 실제로 수량 누락·오입고를 겪은 적이 있는지, 언제 어떻게 발견했는지 묻는 문항 추가 | 채택 | '재고 관리 문제가 손실로 이어진다'는 가정을 소규모 매장 기준으로 검증하는 핵심 질문이다. |
| 발주를 어떤 방식(전화, 문자, 앱, 수기)으로 하는지 묻는 문항 추가 | 채택 | 서비스가 판독 결과를 발주 내역과 대조하는 구조인데, 발주 기록이 남지 않는 매장이라면 대조 기능 자체가 성립하지 않는다. 미처 고려하지 못한 전제였다. |
| 받는 거래명세서의 형태(인쇄, 손글씨, 전자 명세서)와 거래처 수를 묻는 문항 추가 | 채택 | AI의 양식별 판독 정확도를 아직 검증하지 않았다. 실제 양식 분포를 알아야 MVP에서 어떤 양식부터 지원할지 정할 수 있다. |
| 현재 재고 관리 앱(박스히어로 등) 사용 여부와 쓰지 않거나 그만둔 이유를 묻는 문항 추가 | 채택 | 기존 서비스와의 차별점을 입고 확인 과정에 두기로 했으므로, 기존 앱의 불편한 점이 실제로 입고 단계에 있는지 확인이 필요하다. (1-shusbox-2, 5-shusbox-3) |
| 입고 확인을 누가 하는지(사장, 직원, 아르바이트생) 묻는 문항 추가 | 채택 | 사용자가 판독 결과를 수정·확정하는 방식이라 실제 사용자의 숙련도와 권한에 따라 화면 설계가 달라진다. |
| AI 판독 결과를 직접 확인·수정하는 과정을 감수할 의향이 있는지 묻는 문항 추가 | 채택 | 정확도 문제를 '사용자 확인 후 확정'으로 보완하기로 했으므로, 이 추가 단계가 사용자에게 부담인지 확인해야 MVP 가정이 유지된다. |
| 유료 결제 의향과 적정 가격을 묻는 문항 추가 | 보류 | 아직 문제의 존재 여부를 검증하는 단계라 가격 질문은 이르다. 문제 검증 후 다음 조사에서 다룬다. |
| 거래처 단가가 담긴 명세서를 사진으로 올리는 것에 대한 보안·개인정보 우려를 묻는 문항 추가 | 보류 | 중요한 관점이지만 이번 질문지의 목적(문제 확인)과 거리가 있고 문항 수가 늘어난다. 기획서의 '추후 고려 사항'에 기록해 둔다. |
| 대상 업종을 음식점·편의점·카페 등으로 넓혀 업종별로 묻기 | 보류 | 대상을 넓히면 응답이 분산돼 결론을 내기 어렵다. 우선 거래명세서를 자주 받는 업종 한 곳에 집중한다. |

## 제안서 검토 (6단계)

> 제안서를 Claude에게 보여 주고 "처음 읽는 고객이라면 무엇이 이해되지 않는가", "근거 없이 단정한 문장은 무엇인가"를 물어봅니다.

| AI 지적 | 반영 / 보류 | 이유 |
| --- | --- | --- |
| 5-2~5-5의 기능 목록, 가정, 위험, 사전 질문 표가 비어 있는데 초안에 구체적인 항목이 적혀 있었다. | 반영 | 해당 내용은 조사 근거가 없어 초안에서 지우고 `[조사 파일에 없음]`으로 표시했다. 5-1과 5-7에 실제로 적힌 MVP 흐름과 고객사 설정 요청만 남겼다. |
| Ⅳ-12 상태 흐름에서 모든 전이에 담당자와 조건이 있는지 확인해야 한다. | 반영 | 정상 상태 5개와 발주 취소 경로가 있다. 공급처 접수 후 상태를 바꾸는 담당자는 조사 파일에서 특정되지 않아 그 부분을 `[조사 파일에 없음]`으로 표시했다. |
| Ⅳ-13에서 LLM이 최종 입고를 결정하거나 개인정보를 받는 것으로 읽힐 수 있다. | 반영 | 직원이 실물과 판독 결과를 대조·수정하고 확정해야 재고가 바뀌도록 썼고, 거래처 담당자 정보와 사업자 정보는 보내기 전에 가린다고 적었다. |
| Ⅶ-16의 `[사실]` 규칙 R3·R4는 조사 파일에 출처 링크가 있지만, 이 검토에서는 링크 원문을 직접 확인하지 못했다. | 보류 | 03의 조사표에 붙은 `[사실]` 태그는 유지했다. 최종본에 옮기기 전 팀원이 출처 링크를 열어 확인할 필요가 있다. |
