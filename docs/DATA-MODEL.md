# 데이터 구조

> **저장 위치:** `docs/DATA-MODEL.md`

> **사용 방법**
> 1. PRD의 '데이터 구조'를 **확정**하는 문서입니다. PRD와 다르게 쓰지 않고, 확정한 내용을 PRD에도 옮깁니다.
> 2. **상태값은 `domain/03-rules-states-llm.md`의 상태와 똑같이** 씁니다. 이름이 다르면 나중에 테스트가 어긋납니다.
> 3. 모델마다 **핵심 필드 3~5개**부터 시작합니다. 필드를 많이 만들지 않습니다.
> 4. Claude는 빠진 필드와 모순을 **찾아 주기만** 합니다. 어떤 필드를 둘지는 팀이 정합니다.
> 5. 시드(예시) 데이터 3~5건은 오늘 만드는 기능의 화면 확인에 쓰고, 다음 시간 테스트 입력으로도 씁니다.
> 6. **개발자1이 씁니다.** 결정은 팀이 하고, 파일에 적는 것은 개발자1(공유 파일이라 PM이 PR로 올림)입니다.
> 7. `>`로 시작하는 안내 문장은 지워도 됩니다.

- 확정일: (팀 확정 전 — 초안)
- 근거: `PRD.md`(6절 데이터 구조), `03-rules-states-llm.md`(3-2 상태 전이, 3-4 공통 JSON), `backlog.md`(US-01~US-08 인수 조건)

> 아래 필드는 PRD 6절에 있는 것만 옮겼습니다. 타입은 03 3-4 공통 JSON 예시를 보고 적은 **[제안]**이고, 필수 여부는 인수 조건에 근거가 있는 칸만 채웠습니다. 근거가 없으면 `미정`입니다. PRD에 없는데 필요해 보이는 필드는 새로 넣지 않고 맨 아래 '아직 정하지 못한 것'에 질문으로 적었습니다.

## 관계
> 모델 사이 연결을 한 줄씩. 예) 신청 → 글 (신청은 글 하나에 속한다)
- 매장 사용자 → 매장
- 상품 → 매장 (상품 코드는 매장 안에서 중복되지 않는다)
- 발주 건 → 매장
- 발주 건의 줄 → 상품
- 입고 검수 건 → 발주 건 (`검수 종료` 뒤 다시 납품되면 같은 발주에 새 검수 건이 생긴다 — US-06)
- 판독 결과(줄) → 입고 검수 건 (연결 필드는 PRD에 없음, 아래 미정 참고)
- 판독 결과 줄의 item_candidates → 상품 (같은 매장 상품만, 최대 3개)
- 판독 로그 → 입고 검수 건 (재업로드하면 여러 줄일 수 있음)
- 변경 이력 → 입고 검수 건, 매장 사용자(changed_by)
- 재고 → 매장, 상품 (매장·상품 조합마다 1줄)

## 상태값 (핵심 대상의 `status`)

핵심 대상: **입고 검수 건** (03 3-2). DB에 저장할 값은 03 문서의 한국어 이름을 그대로 쓴다 (영문 코드로 바꿀지는 미정).

| 상태값 | `03` 문서의 상태 이름 | 누가 바꿀 수 있나 | 어떤 경우에 바뀌나 |
| --- | --- | --- | --- |
| 업로드 대기 | 업로드 대기 | 시스템 | 연결된 발주 건이 `입고 대기`가 될 때 만들어짐 / `판독 중`에서 판독 실패 시 되돌아옴 |
| 판독 중 | 판독 중 | 매장 직원 | `업로드 대기` 건에 거래명세서 사진·PDF를 올림 (사진·PDF가 아니면 바뀌지 않음) |
| 직원 확인 대기 | 직원 확인 대기 | 시스템(OCR+LLM 판독 완료) / 매장 직원(확정 취소, 반려 후 재검수) | 판독이 끝남 / 사장 처리 전 직원이 확정 취소 / `반려` 뒤 직원이 재검수 |
| 사장 승인 대기 | 사장 승인 대기 | 매장 직원(확정) → 시스템(분류) | 확정 내용에 수량 차이·파손·단가 변경·발주에 없는 품목이 있음(예외 건). 예외 사유 필수, 재고 안 바뀜 |
| 승인 | 승인 | 매장 사장님 | 예외 내용을 받아들임 |
| 반려 | 반려 | 매장 사장님 | 반려 사유를 입력하고 받아들이지 않음. 재고 안 바뀜 |
| 재고 반영 완료 | 재고 반영 완료 | 매장 직원(확정) → 시스템 / 시스템(승인 후) | 일반 건 확정 / `승인` 뒤 승인 수량·단가로 반영. 되돌릴 수 없음 |
| 검수 종료 | 검수 종료 | 매장 사장님 | `반려` 뒤 공급처에 반품·정정을 요청하고 닫음. 다시 열 수 없음 |

발주 건 `status` (US-01·US-02, 03 3-2):

| 상태값 | 누가 바꿀 수 있나 | 어떤 경우에 바뀌나 |
| --- | --- | --- |
| 발주 초안 | 매장 사장님 | 상품·수량(1 이상)을 골라 저장 |
| 발주 확인 완료 | 매장 사장님 | `발주 초안`을 승인 (수량 한도 초과면 경고 후 다시 확인, R7) |
| 공급처 전달 완료 | 매장 사장님 | 공급처 전달 완료로 표시 |
| 입고 대기 | 시스템 | `공급처 전달 완료` 다음. 이때 입고 검수 건 1건 생성 |
| 입고 완료 | 시스템 | 연결된 입고 검수 건이 `재고 반영 완료`가 됨 |
| 발주 취소 | 매장 사장님 | `발주 초안`에서 취소. 끝 상태 |

- 취소·반려 경로로 가는 상태:
  - 입고 검수 건: `판독 중 → 업로드 대기`(판독 실패), `사장 승인 대기 → 직원 확인 대기`(직원 확정 취소), `사장 승인 대기 → 반려`, `반려 → 직원 확인 대기`(재검수), `반려 → 검수 종료`
  - 발주 건: `발주 초안 → 발주 취소`
- LLM이 상태를 **직접 바꾸지 않고**, 사람이나 규칙이 최종 결정하는 곳:
  - LLM 출력(판독 결과 줄)은 `직원 확인 대기` 화면의 초안이다. `재고 반영 완료`·`사장 승인 대기`로 가는 것은 직원 확정 뒤 시스템 규칙(발주와 비교)이 정한다
  - 재고(`재고.quantity`)는 직원 확정(일반 건) 또는 사장님 승인(예외 건) 뒤에만 시스템이 바꾼다 (R3)
  - `uncertain_fields`, 규칙 검증 실패 칸, 후보 없음·후보 2개 이상인 줄은 직원이 확인해야 확정할 수 있다 (US-04)

## LLM에 보내지 않을 정보
> 제안서 Ⅳ-13과 `03` 문서에서 가져옵니다. 이 필드는 LLM 호출 입력에 포함하지 않습니다.

| 모델 | 필드 | 보내지 않는 이유 |
| --- | --- | --- |
| (명세서 원본) | 거래처 담당자 이름·연락처 | 개인정보. 직원 기기 안에서 가린 뒤 보낸다 (03 3-4 L1, US-03). 뼈대 단계는 서버 쪽 임시 마스킹 (STACK.md) |
| (명세서 원본) / 발주 건 | 사업자 정보, supplier | 사업자 정보는 발주 건에 이미 있으므로 공통 JSON에 넣지 않는다 (03 3-4) |
| (명세서 원본) | 원본 사진·PDF 파일 | 외부 LLM으로 보내지 않는다. OCR이 읽은 글자만 보낸다 (US-03) |
| 매장 사용자 | 사용자 정보 전체 | L1 입력(OCR 글자, 발주 품목·수량, 상품명·규격)에 필요 없음 (03 3-4 L1 입력 목록) |
