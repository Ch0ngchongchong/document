# 프로젝트 제안서 초안

## 제안 요약

### 서비스 한 줄 정의

**딱 재고**는 거래명세서 사진이나 PDF에서 상품명·수량·단가를 표로 정리하고 발주 내용과 다른 줄을 표시해, 매장 직원이 실물과 대조·확정한 수량만 재고에 반영하도록 돕는 거래명세서 기반 매장 입고 확인 서비스다. (출처: topic-selection 4-4~4-5, mvp 5-1, 03 3-4 L1)

### 해결할 문제

소규모 매장 사장님은 종이 거래명세서를 보며 입고 상품과 수량을 엑셀에 한 줄씩 입력한다. 입력 과정에서 상품 정보가 빠지거나 오타가 생길 수 있다. (출처: topic-selection 4-4, 02 2-2 순서 2)

### 핵심 기능 3가지

1. 사장님이 상품과 수량으로 발주를 만들고 승인한 뒤, 공급처에 전달했음을 표시한다. (출처: mvp 5-1)
2. 거래명세서 사진·PDF를 읽어 상품명·수량·단가를 표로 만들고, 발주 내용과 다른 줄을 표시한다. (출처: mvp 5-1, 03 3-4 L1)
3. 매장 직원이 판독 결과를 실물과 대조해 수정·확정한 수량만 재고에 반영한다. (출처: mvp 5-1, 03 3-4 L1)

### 기대 효과

거래명세서 한 장을 재고에 반영하는 시간을 현재의 절반 이하로 줄이는 것을 목표로 한다. 현재 처리 시간은 클라이언트 미팅에서 확인한다. (출처: topic-selection 4-4)

월 실사에서 입고 기록과 실제 재고가 다른 줄 수를 현재보다 줄이고, LLM 판독 결과에서 직원이 고치는 줄 비율은 10% 이하로 하는 것을 목표로 한다. 현재 불일치 줄 수는 클라이언트 미팅에서 확인한다. (출처: topic-selection 4-4)

### 고객께 요청드리는 것

첫 데모 범위를 정하기 위해 매장 종류와 상품 수, 거래명세서·상품 목록 샘플 제공 가능 여부, POS나 공급처 시스템 연동 필요 여부를 확인하고자 한다. (출처: mvp 5-7)

## Ⅰ. 제안 개요

### 1. 제안 배경

현재 조사한 매장 흐름에서는 사장님이 재고를 확인하고 종이 거래명세서의 상품과 수량을 엑셀에 입력한다. 상품이 많으면 재고 확인에 시간이 오래 걸리고, 수기 입력 과정에서 누락이나 오타가 생길 수 있다. (출처: 02 2-2 순서 1~2)

재고관리 소프트웨어의 사용자 반응과 발주·재고 보유·품절 비용 절감 가능성을 다룬 연구 자료가 조사됐다. [사실] 해당 연구가 이 주제를 다룬다는 점을 확인했다. (출처: 02 2-5 카드 2, 03 3-5, 카드 1-shusbox-2)

소비기한과 입고 기준일을 고려한 재고관리 연구도 조사됐다. [사실] 해당 주제의 연구가 있음을 확인했다. (출처: 02 2-5 카드 3, 03 3-5, 카드 5-kimjiwoon3472-3)

기존 재고 앱이 바코드 입출고와 안전재고 알림을 제공하더라도 거래명세서와 발주 내용을 대조하는 일은 사람이 한다는 점은 조사 과정의 [추정]이다. (출처: topic-selection 4-4, 02 2-4)

### 2. 제안 목적

거래명세서의 상품명·수량·단가를 표로 정리하고 발주 내용과 다른 부분을 표시해, 직원이 실제 물건과 대조하고 입고를 확정하는 일을 돕는다. 직원이 확인하기 전에는 재고를 바꾸지 않는다. (출처: mvp 5-1, 03 3-4 L1)

### 3. 제안 범위

첫 데모에서는 발주 작성·승인, 공급처 전달 표시, 입고 대기, 거래명세서 업로드·판독, 실물 대조·수정·확정을 다룬다. 직원이 확정한 수량만 재고에 더한다. (출처: mvp 5-1)

판매량 예측·발주 수량 추천, POS 연동을 통한 판매 시 재고 자동 차감, 공급처에 문자·앱으로 자동 발주 전송, 부분 입고·반품, 공급처 취소 승인·거절 경로는 첫 데모에서 제외한다. (출처: mvp 5-1)

## Ⅱ. 현황 분석

### 4. 현재 방식과 문제점

현재 조사된 흐름은 다음과 같다. (출처: 02 2-2)

1. 사장님이 매장에 남은 상품을 직접 확인하고 종이에 메모한다. 상품이 많으면 시간이 오래 걸리고 정확한 수량을 파악하기 어렵다. (출처: 02 2-2 순서 1)
2. 거래명세서를 보고 입고 상품과 수량을 엑셀에 입력한다. 일일이 입력하므로 누락이나 오타가 생길 수 있다. (출처: 02 2-2 순서 2)
3. POS나 판매 기록을 확인해 판매량을 파악하고 재고를 갱신한다. 판매 데이터와 실제 재고가 다를 수 있고 재고를 수동으로 관리해야 한다. (출처: 02 2-2 순서 3)
4. 판매량과 남은 재고를 확인해 추가 주문을 판단한다. 날씨나 요일에 따른 수요 변화를 예측하기 어렵고 발주량이 경험에 의존할 수 있다. (출처: 02 2-2 순서 4)
5. 공급처별 가격과 주문 조건을 확인해 발주 수량을 정한다. 공급처마다 주문 방식이 다를 수 있고 가격과 최소 주문 수량을 비교하기 번거롭다. (출처: 02 2-2 순서 5)
6. 공급처에 발주하고 유통기한이 임박하거나 폐기할 상품을 확인한다. 발주 내역을 따로 관리해야 하며 유통기한을 놓치거나 과잉 발주로 폐기할 수 있다. (출처: 02 2-2 순서 6)

사장님은 재고 확인과 발주 승인을 맡고, 매장 직원은 입고 확인과 재고 관리를 맡는다. 공급업체는 발주를 확인하고 상품을 납품한다. (출처: 02 2-1)

재고 관리에는 상품명·바코드·판매가, 재고 수량, 매입 단가·마진, 거래처 정보가 쓰인다. 거래처 담당자 이름과 연락처는 개인정보로 표시돼 있다. (출처: 02 2-3)

A는 발주 내용과 명세서를 대조하고 직원이 확정하는 규칙이 분명하다(① 3점). 부분 입고·파손·누락·품목 불일치가 경계 사례다(② 3점). 입고 상태와 직원 확인 권한이 제시돼 있다(③ 3점). 거래명세서와 공급처 문의가 외부 접점이지만 연동 방식은 미정이다(④ 2점). 단일 입고 확인 흐름을 시연할 수 있으나 양식과 판독 정확도가 확인되지 않았다(⑤ 2점). 수기 판독·입력을 줄이고 직원이 결과를 확인한다(⑥ 3점). 첫인상 조사에서 한 팀원이 수기 입력 문제를 언급했지만 팀 전체 선호는 확인되지 않았다(⑦ 2점). (출처: topic-selection 4-3 점수 근거 A)

B는 POS 판매량과 실사 수량 차이를 규칙으로 계산하고 테스트할 수 있다(① 3점). 누락 판매·반품·파손·실사 오류 등이 경계 사례다(② 3점). 실사부터 승인·반려까지의 흐름은 4-2에서 새로 세워 권한과 근거가 덜 구체적이다(③ 2점). POS가 외부 접점이지만 연동 방식은 미정이다(④ 2점). POS 자료 연결과 실사 확인이 필요해 초기 구현 가능성을 중간으로 봤다(⑤ 2점). LLM 점수 2는 차이 사유 메모를 분류·요약해 조정 사유 초안을 만드는 활용안을 전제로 한 평가이며, 3-4에 이미 적힌 후보가 있다는 뜻은 아니다. 수량 계산은 규칙으로 한다(⑥ 2점). 첫인상 조사에서 수기 재고·입력 문제가 나왔지만 팀 전체 선호는 확인되지 않았다(⑦ 2점). (출처: topic-selection 4-2 B, 4-3 점수 근거 B)

C는 안전재고 기준은 있으나 입고 예정 정보를 언제·어떻게 반영할지 규칙이 더 필요하다(① 2점). 입고 지연·취소 승인·거절·부분 입고·안전재고 도달 등이 경계 사례다(② 3점). 발주 초안부터 입고 완료까지 상태와 사장님·공급처 권한이 제시돼 있다(③ 3점). 공급처 응답과 판매·날씨 정보가 외부 접점이지만 데이터 확보 방식은 미정이다(④ 2점). 실제 입고·판매 데이터 연결 범위가 불확실하다(⑤ 2점). LLM 설명·메시지 초안은 돕지만 입고 예정과 품절의 구분은 규칙·데이터에 달려 있다(⑥ 2점). 팀 첫인상에서 수요 예측·과잉 재고·폐기 우려가 여러 번 나왔다(⑦ 3점). (출처: topic-selection 4-3 점수 근거 C)

A는 18점으로 가장 높고 C는 17점으로 1점 차이다. ④·⑤ 점수에는 외부 연동과 실제 데이터 확보가 확인되지 않은 점이 반영됐다. (출처: topic-selection 4-3)

### 8. 최종 선정 이유

최종 주제는 거래명세서 기반 매장 입고 확인 서비스다. 후보 A가 18점으로 가장 높았고, 거래명세서 판독과 발주 내용 대조를 통해 입고 기록의 누락과 오타를 줄이는 방향으로 정했다. (출처: topic-selection 4-4~4-5)

클라이언트 미팅에서 거래명세서 수기 입력이 실제로 큰 문제인지, 판독 시간과 오류 발생 현황이 어떤지 확인한다. 핵심 문제가 아니거나 자동 판독의 실효성이 낮으면 세부 주제를 다시 검토한다. (출처: topic-selection 4-5)

## Ⅳ. 제안 내용

### 9. 서비스 개요

사장님은 상품과 수량을 입력해 발주를 만들고 승인한다. 공급처에 발주를 보낸 뒤 전달 완료로 표시한다. 상품이 도착하면 직원이 거래명세서를 올려 판독 결과를 실물 및 발주 내용과 대조하고, 수정·확정한다. 직원이 확정한 수량만 재고에 반영한다. (출처: mvp 5-1, 03 3-4 L1)

### 10. 목표 흐름 (To-Be)

1. 사장님이 상품과 수량을 입력해 발주를 만들고 승인한다. (출처: mvp 5-1)
2. 공급처에 발주를 전달하고 전달 완료로 표시한다. 공급처가 접수하면 입고를 기다린다. (출처: mvp 5-1, 03 3-2)
3. 물건이 도착하면 직원이 거래명세서 사진을 올린다. 사진·PDF에서 상품명·수량·단가를 표로 만들고 발주 내용과 다른 줄을 표시한다. (출처: mvp 5-1, 03 3-4 L1)
4. 직원이 판독 결과를 실제 물건과 대조해 수정·확정한다. 확정한 수량만 재고에 반영한다. (출처: mvp 5-1, 03 3-4 L1)

### 11. 주요 기능 목록

첫 데모 흐름은 발주 작성·승인, 공급처 전달 표시, 입고 대기, 거래명세서 업로드·판독, 실물 대조·수정·확정이다. (출처: mvp 5-1)

### 12. 상태 흐름

| 현재 상태 | 다음 상태 | 누가 바꾸나 | 조건 |
| --- | --- | --- | --- |
| 발주 초안 | 발주 확인 완료 | 매장 사장님 | 상품과 수량을 입력해 발주를 만들고 승인한다. [가정] |
| 발주 확인 완료 | 공급처 전달 완료 | 매장 사장님 | 공급처에 발주를 전달하고 전달 완료로 표시한다. [가정] |
| 공급처 전달 완료 | 입고 대기 | 공급처 또는 시스템 | 공급처가 발주를 접수한다. [가정] |
| 입고 대기 | 입고 완료 | 매장 직원 | 실제 입고된 상품과 수량을 확인하고 재고에 반영한다. [가정] |
| 발주 초안 | 발주 취소 | 사장님 | 공급처에 보내기 전에 발주를 취소한다. |

정상 흐름은 발주 초안 → 발주 확인 완료 → 공급처 전달 완료 → 입고 대기 → 입고 완료의 5개 상태다. 발주 초안에서 공급처에 보내기 전에 취소하는 경로가 있다. (출처: 03 3-2 표, mvp 5-1)

### 13. LLM 활용 방안

LLM에는 공급처 거래명세서 사진·PDF와 해당 발주 건의 품목·수량 목록을 넣는다. 상품명·수량·단가 표를 만들고 발주 내용과 다른 줄을 표시한다. (출처: 03 3-4 L1)

매장 직원은 판독 결과를 실물과 대조해 고치고 확정한다. LLM이 재고를 바꾸지 않으며, 직원이 확정해야 재고 수량이 바뀐다. (출처: 03 3-4 L1, mvp 5-1)

거래처 담당자 이름·연락처와 사업자 정보는 LLM에 보내기 전에 지우거나 가린다. 잘못 읽은 수량·단가는 재고와 매입 단가를 틀리게 할 수 있으므로 사람이 확인한다. (출처: 03 3-4 L1)

## Ⅶ. 전제 조건, 위험, 고객 확인 요청

### 16. 규칙·가정

**적용할 규칙**

- 발주서만 작성한 단계에서는 재고가 바뀌지 않고, 실제 입고 처리 후 재고에 더한다. 부분 입고는 검수한다. [사실] (출처: 03 3-1 R3)
- 매입한 물건을 반품하면 반품 수량만큼 재고에서 뺀다. [사실] (출처: 03 3-1 R4)
- 첫 데모에서는 직원이 입고 내용을 확인하고 확정해야 재고가 바뀐다. (출처: mvp 5-1)

### 17. 위험과 대응

| 위험 | 생기면 | 대응 |
| --- | --- | --- |
| 거래명세서 판독 오류 | 수량·단가를 잘못 읽으면 재고와 매입 단가가 틀어질 수 있다. | 직원이 실제 물건과 대조해 수정·확정한 뒤에만 재고에 반영한다. |

(출처: 03 3-4 L1, mvp 5-1)

### 18. 질문 3가지·고객사 설정 요청

**미리 보낼 질문 3가지**

1. 거래명세서 한 장을 재고에 반영하는 데 현재 얼마나 걸리고, 주로 어떤 입력 오류가 생기나요? (출처: topic-selection 4-4, 02 2-2)
2. 입고 확인은 현재 누가 맡고, 명세서와 실제 물건이 다를 때 누가 수정·확정하나요? (출처: 02 2-1, mvp 5-1)
3. 첫 데모 검토를 위해 거래명세서와 상품 목록 샘플을 제공할 수 있나요? POS나 공급처 시스템 연동도 필요한가요? (출처: mvp 5-7)

**미리 정해 주시거나 제공해 주실 내용**

- 매장 종류와 상품 수, 입고 확인을 맡는 사람 (출처: 02 2-1, mvp 5-7)
- 거래명세서 샘플과 상품 목록 제공 가능 여부 (출처: mvp 5-7)
- POS나 공급처 시스템 연동이 필요한지 (출처: mvp 5-7)

샘플이 있으면 상품명이나 단위가 상품 목록과 다른 사례를 확인한다. 샘플이 없으면 제공 가능한 시기나 테스트 자료 제공 여부를 확인한다. POS나 공급처 연동이 꼭 필요하면 첫 데모 범위를 다시 정한다. (출처: mvp 5-7)
