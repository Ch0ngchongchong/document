# 프로젝트 제안서 초안

## 제안 요약

### 서비스 한 줄 정의

**사진 한 장 입고**는 매장 직원이 거래명세서 사진이나 PDF를 올리면 품목·수량·단가를 표로 정리하고, 발주 내용과 다른 줄을 보여 주는 매장 입고 확인 서비스다. 직원이 실물과 대조해 고친 뒤 확정해야 재고가 바뀐다. (출처: topic-selection 4-4, mvp 5-1)

### 해결할 문제

소규모 매장 사장님은 공급처에서 물건이 들어올 때 종이 거래명세서의 품목과 수량을 손으로 옮겨 적는다. 그 과정에서 누락이나 오타 없이 재고 기록을 맞추기 어렵다. (출처: topic-selection 4-4, 02 2-2)

### 핵심 기능 3가지

1. 상품 정보를 등록하고 거래명세서 판독 결과와 맞춘다. (출처: mvp 5-2 F-01)
2. 상품과 수량을 넣어 발주를 만들고 승인·취소하며, 공급처에 전달한 상태를 표시한다. (출처: mvp 5-2 F-02)
3. 거래명세서를 읽어 발주 내용과 대조하고, 직원이 확인한 수량만 재고에 반영한다. (출처: mvp 5-2 F-03, F-04)

### 기대 효과

거래명세서 한 장을 재고에 반영하는 시간을 현재의 절반 이하로 줄이는 것을 목표로 한다. 현재 처리 시간은 클라이언트 미팅에서 확인한다. (출처: topic-selection 4-4)

입고 기록과 실제 재고가 다른 줄 수를 줄이고, LLM 판독 결과에서 직원이 고치는 줄 비율을 10% 이하로 하는 것을 목표로 한다. 현재 불일치 줄 수는 클라이언트 미팅에서 확인한다. (출처: topic-selection 4-4)

### 고객께 요청드리는 것

현재 거래명세서를 재고에 등록할 때 가장 불편한 점, 한 건을 확인하고 입력하는 데 걸리는 시간, 발주 내용과 실제 입고 내용이 얼마나 자주 다른지 알려 주시기 바란다. 첫 데모 범위를 정할 수 있도록 거래명세서와 상품 목록의 익명화된 예시를 제공할 수 있는지, POS나 공급처 연동이 필요한지도 함께 확인하고자 한다. (출처: mvp 5-5 1~3, mvp 5-7)

## Ⅰ. 제안 개요

### 1. 제안 배경

현재 조사한 매장 흐름에서는 사장님이 재고를 직접 확인하고, 종이 거래명세서의 상품과 수량을 엑셀에 입력한다. 상품이 많으면 확인에 시간이 오래 걸리고, 수기 입력 중 누락이나 오타가 생길 수 있다. (출처: 02 2-2)

재고관리 소프트웨어의 이용자 반응과 발주·재고 보유·품절 비용을 다룬 자료가 확인됐다. 다만 구체적인 절감 수치와 우리 서비스 도입 시 효과는 조사 파일에서 확인되지 않았다. [사실] 연구가 해당 주제를 다룬다는 점은 확인했고, 특정 매장에 같은 효과가 있다는 점은 미확인이다. (출처: 03 3-5, 카드 1-shusbox-2)

기존 재고 앱은 바코드 입출고나 안전재고 알림 등을 제공하지만, 거래명세서와 발주 내용을 대조하는 일은 사람이 한다는 것이 우리 조사에서 나온 추정이다. [추정] (출처: topic-selection 4-4, 02 2-4)

### 2. 제안 목적

거래명세서에 적힌 품목·수량·단가를 표로 정리하고 발주 내용과 다른 부분을 표시해, 직원이 실제 물건과 대조하고 재고를 확정하는 일을 돕는다. 판독 결과가 틀리더라도 직원이 확인하기 전에는 재고가 바뀌지 않게 한다. (출처: mvp 5-1, mvp 5-2 F-03~F-04)

### 3. 제안 범위

첫 데모에는 상품 등록, 발주 작성·승인·취소, 거래명세서 판독, 입고 대조·확정을 포함한다. 거래명세서 판독 결과는 직원이 고쳐 확정하고, 확정한 수량만 재고에 더한다. (출처: mvp 5-1, mvp 5-2 F-01~F-04)

부분 입고·누락 문의와 반품 처리는 선택 기능으로 둔다. 판매량 예측·발주 수량 추천, POS를 통한 판매 시 재고 자동 차감, 공급처에 문자나 앱으로 자동 발주하는 기능, 공급처 취소 승인·거절 흐름은 첫 데모에서 제외한다. (출처: mvp 5-1, mvp 5-2 F-05~F-06)

첫 데모에서 지원할 거래명세서 양식 수와 테스트에 쓸 상품 수는 [조사 파일에 없음]. 클라이언트가 제공할 수 있는 자료를 확인한 뒤 정한다. (출처: mvp 5-5 8, mvp 5-7)

## Ⅱ. 현황 분석

### 4. 현재 방식과 문제점

현재 흐름은 다음과 같다. (출처: 02 2-2)

1. 사장님이 매장에 남은 상품을 직접 확인하고 종이에 메모한다. 상품이 많으면 시간이 오래 걸리고 정확한 수량을 파악하기 어렵다. (출처: 02 2-2 1)
2. 거래명세서를 보며 입고 상품과 수량을 종이나 엑셀에 기록한다. 일일이 입력하다 보니 누락이나 오타가 생길 수 있다. (출처: 02 2-2 2)
3. POS나 판매 기록을 확인해 판매량을 파악하고 재고를 갱신한다. 판매 데이터와 실제 재고가 다를 수 있고, 재고를 수동으로 관리해야 한다. (출처: 02 2-2 3)
4. 판매량과 남은 재고를 보고 추가 발주 여부와 수량을 정한다. 날씨나 요일에 따른 수요를 예측하기 어려워 경험에 의존할 수 있다. (출처: 02 2-2 4)
5. 공급처별 가격과 주문 조건을 확인해 전화·문자·메신저·주문 앱으로 발주한다. 공급처마다 방식이 달라 비교와 기록이 번거롭다. (출처: 02 2-2 5~6)

사장님은 재고 확인과 발주 승인을 맡고, 매장 직원은 입고 확인과 재고 관리를 맡을 수 있다. 공급업체는 발주를 확인하고 상품을 납품한다. (출처: 02 2-1)

상품명·바코드·판매가, 재고 수량, 매입 단가와 거래처 정보가 재고 관리에 쓰인다. 거래처 담당자 이름과 연락처는 개인정보로 분류돼 있다. (출처: 02 2-3)

## Ⅲ. 세부 주제 선정 과정

### 6. 검토한 후보

| 후보 | 문제 |
| --- | --- |
| A | 사장님이 종이 거래명세서를 보고 입고 상품과 수량을 손으로 입력해 재고 기록에 누락·오타가 생길 수 있다. (출처: topic-selection 4-1 A) |
| B | 판매 수량을 직접 파악해 재고를 수동 갱신하면서 판매 기록과 실제 재고가 맞지 않을 수 있다. (출처: topic-selection 4-1 B) |
| C | 안전재고 아래로 떨어진 상품이 곧 입고될지 실제 품절인지 구분하지 못해 품절을 늦게 알아챌 수 있다. (출처: topic-selection 4-1 C) |

### 7. 선정 기준과 평가

| 기준 | A 거래명세서 입력 | B 판매 재고 갱신 | C 안전재고·입고예정 구분 |
| --- | ---: | ---: | ---: |
| 규칙의 명확성 | 3 | 3 | 2 |
| 경계 사례 | 3 | 3 | 3 |
| 상태·권한 | 3 | 2 | 3 |
| 외부 접점 | 2 | 2 | 2 |
| 8주 MVP 가능성 | 2 | 2 | 2 |
| LLM의 쓸모 | 3 | 2 | 2 |
| 팀의 흥미 | 2 | 2 | 3 |
| **합계** | **18** | **16** | **17** |

A는 발주 내용과 명세서를 대조하고 직원이 확정하는 규칙이 분명하다. 판독과 입력을 직접 줄이는 LLM 활용이 있고, 직원이 결과를 확인한다. (출처: topic-selection 4-3 점수 근거, mvp 5-1)

B의 상태 흐름은 조사 근거 없이 새로 세운 것이며, C는 판매·입고 데이터 연결 범위를 더 확인해야 한다. A가 18점으로 가장 높아 거래명세서 기반 입고 확인을 선택했다. A와 C의 점수 차이는 1점이다. (출처: topic-selection 4-2~4-5)

### 8. 최종 선정 이유

최종 주제는 **거래명세서 기반 매장 입고 확인 서비스**다. 종이 거래명세서의 품목과 수량을 수기로 옮기는 문제에 집중하고, LLM이 판독한 결과를 직원이 확인한 다음에만 재고를 바꾸도록 했다. (출처: topic-selection 4-4~4-5, mvp 5-1)

클라이언트 미팅에서 거래명세서 수기 입력이 실제로 큰 문제인지, 판독 시간과 오류가 어느 정도인지 확인한다. 이 문제가 핵심이 아니거나 자동 판독의 실효성이 낮다고 판단되면 주제를 다시 검토한다. (출처: topic-selection 4-5)

## Ⅳ. 제안 내용

### 9. 서비스 개요

사장님은 상품과 수량을 입력해 발주를 만들고 승인한다. 공급처에 보낸 뒤에는 전달 상태를 표시한다. 상품이 도착하면 직원이 거래명세서 사진이나 PDF를 올리고, 판독 결과를 실물 및 발주 내용과 대조해 확정한다. 확정된 수량만 재고에 반영한다. (출처: mvp 5-1)

### 10. 목표 흐름 (To-Be)

1. 직원이 상품 정보를 등록하고, 거래명세서에 적힌 상품이 등록 상품과 맞는지 확인한다. (출처: mvp 5-2 F-01)
2. 사장님이 상품과 수량을 넣어 발주를 만들고 승인한다. 공급처에 전달한 뒤 화면에서 전달 완료로 표시한다. (출처: mvp 5-1, mvp 5-2 F-02)
3. 공급처가 발주를 접수하면 입고 대기 상태로 둔다. (출처: mvp 5-1)
4. 물건이 도착하면 직원이 거래명세서 사진이나 PDF를 올린다. 판독 결과에서 품목·수량·단가와 발주 내용이 다른 줄을 확인한다. (출처: mvp 5-1, mvp 5-2 F-03)
5. 직원이 실제 물건과 판독 결과를 대조해 필요한 내용을 고친다. 직원이 확정한 뒤에만 재고를 갱신한다. (출처: mvp 5-1, mvp 5-2 F-04)

| 입고 확인중 | 입고 완료 | 매장 직원 | 실물과 대조해 수정한 뒤 확정한다. 확정 수량만 재고에 반영한다. |
| 발주 초안 | 발주 취소 | 사장님 | 공급처에 보내기 전에 취소한다. |

(출처: topic-selection 4-2 A, mvp 5-1~5-2, 03 3-2)

발주 초안부터 입고 완료까지 정상 상태가 7개이며, 공급처 전달 전 취소 경로가 있다. 부분 입고·누락 문의와 불량 반품 경로는 선택 기능으로 두고 첫 데모 뒤에 우선순위를 정한다. (출처: mvp 5-1~5-2, topic-selection 4-2 A)

### 13. LLM 활용 방안

LLM에는 거래명세서 사진·PDF와 해당 발주 건의 상품·수량 목록을 넣는다. LLM은 상품명·수량·단가 표를 만들고 발주 내용과 다른 줄을 표시한다. (출처: 03 3-4 L1)

매장 직원은 판독 결과를 실제 물건과 대조하고 수정한 뒤 확정한다. LLM은 재고를 바꾸지 않으며 직원이 확정해야 재고가 바뀐다. (출처: 03 3-4 L1, mvp 5-1)

거래처 담당자 이름·연락처와 사업자 정보는 LLM에 보내기 전에 가린다. 가릴 곳을 확인하지 못하면 전송하지 않고 직접 입력으로 넘어간다. 판독이 실패하거나 잘못돼도 직원 확인 전에는 재고를 바꾸지 않는다. (출처: 03 3-4 L1, mvp 5-4)

## Ⅶ. 전제 조건, 위험, 고객 확인 요청

### 16. 규칙·가정

**적용할 규칙**

- 발주서를 작성한 것만으로 재고를 바꾸지 않는다. 실제 입고를 확인하고 처리해야 재고에 더한다. [사실] (출처: 03 3-1 R3)
- 입고 상품이 주문 수량보다 적거나 파손됐으면 받은 수량을 확인하고 부분 입고로 처리한다. [사실] (출처: 03 3-1 R3)
- 매입한 물건을 반품하면 반품 수량만큼 재고에서 뺀다. [사실] (출처: 03 3-1 R4)
- 첫 데모에서는 직원이 입고 내용을 확인하고 확정해야 재고가 바뀐다. (출처: mvp 5-1, mvp 5-2 F-04)

**미팅에서 확인할 가정**

5-3에는 “가정이 없음”으로 적혀 있지만, mvp 5-5 질문에는 확인되지 않은 가정이 연결돼 있다. 이 초안에서는 다음 내용을 `[가정]`으로 두고 미팅에서 확인한다. (출처: mvp 5-3, mvp 5-5)

- [가정] 거래명세서 수기 입력이 현재 가장 불편한 문제다. (출처: mvp 5-5 1)
- [가정] 거래명세서 한 건을 재고에 등록하는 시간을 줄이는 것이 의미 있는 성과다. (출처: mvp 5-5 2)
- [가정] 발주 내용과 실제 입고 내용의 대조에서 오류가 발생한다. (출처: mvp 5-5 3)
- [가정] 직원이나 사장님이 LLM 판독 결과를 확인하고 입고를 확정할 수 있다. (출처: mvp 5-5 4, 7)

### 18. 질문 3가지·고객사 설정 요청

**미리 보낼 질문 3가지**

1. 현재 거래명세서를 재고에 등록하는 과정에서 가장 불편한 점은 무엇인가요? (출처: mvp 5-5 1)
2. 거래명세서 한 건을 확인하고 입력하는 데 평균적으로 얼마나 걸리나요? (출처: mvp 5-5 2)
3. 거래명세서의 품목과 수량을 발주 내용과 대조하는 과정에서 오류가 자주 발생하나요? (출처: mvp 5-5 3)

**미리 정해 주시거나 제공해 주실 내용**

- 매장 종류와 상품 수, 입고 확인을 맡는 사람 (출처: 02 2-1, mvp 5-7)
- 거래명세서와 상품 목록의 예시를 제공할 수 있는지, 거래처 이름·연락처를 가릴 수 있는지 (출처: 02 2-3, mvp 5-4, mvp 5-7)
- POS나 공급처 시스템 연동이 필요한지, 첫 데모에서 수동으로 상태를 표시해도 되는지 (출처: mvp 5-1, mvp 5-7)

위 설정 요청은 현재 계획을 바탕으로 한 `[가정]`이며, 클라이언트 답변에 따라 첫 데모 범위를 조정한다. (출처: mvp 5-1, mvp 5-7)
